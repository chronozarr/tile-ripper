# Frozen Sentinel COG request accounting

The measured **75,988,992 versus 56,819,712 response-body bytes** on
several-large differ entirely through repeated byte coverage. Both original
implementations request the same union of physical source bytes. This is
established from all three preserved matched latency repetitions, rather than
inferred from their elapsed times or their configured cache sizes.

The benchmark-only [accountant](../../bench/cog_io_trace.py) reads TIFF IFDs,
tile offsets and compressed byte counts from all image levels of the frozen
mirrors. It intersects every logged HTTP range with those intervals and tracks
previously covered byte intervals. Its 1,936 native block offset/size entries
across 16 sources were independently checked against rasterio/GDAL TIFF tags.
No samples are decoded by that accountant. Exact accounting, every several-large
request and every touched block are in [trace-accounting.json](trace-accounting.json).
Complete detailed traces remain under ignored `prototype-output/cog-efficiency/`.

| Several-large byte classification | Matched GDAL | Original Tile-Ripper | Extra Tile-Ripper |
| --- | ---: | ---: | ---: |
| Selected native compressed imagery | 37,648,411 | 56,533,689 | 18,885,278 |
| Unselected native/overview imagery | 19,145,719 | 19,404,355 | 258,636 |
| Exact TIFF metadata storage | 24,142 | 48,284 | 24,142 |
| Other bytes: padding/block leaders/trailers | 1,440 | 2,664 | 1,224 |
| **Total source response bodies** | **56,819,712** | **75,988,992** | **19,169,280** |
| GET requests | 30 | 48 | 18 |
| HEAD requests | 24 | 48 | 24 |

The selected source blocks are columns 6 and 7, rows 1 and 2, in each of six
native 1,024-pixel-tiled COGs: 24 compressed blocks. Repeated selected payload
is confined to the 12 column-7 blocks. Twelve unselected neighboring native
blocks contribute 87,298 repeated bytes, and six tiny overview blocks in header
responses contribute 171,338 repeated bytes. A block touched by two requests is
not necessarily duplicated: GDAL splits some blocks across adjacent ranges
without transferring a byte twice. The accountant distinguishes these cases.

All six original Tile-Ripper assets fetch their initial 32-KiB range twice,
adding 196,608 bytes. The other 18,972,672 excess bytes are repeated imagery
ranges. For example, source `/0.tif` retrieves `86097920–89047039`, then also
`86097920–87605247`; its second source row has an analogous overlap.
Exact duplicate intervals and per-source totals are preserved in the JSON.
Calling all header-range bytes metadata would be incorrect: most of those bytes
belong to a tiny overview image, not TIFF tags.

## Reader reuse, concurrency, order and caches

Original Tile-Ripper assigns each successive output window from a shared task
index to an available worker. Several handles therefore decode windows from the
same source tile concurrently. The matched GDAL control keeps all windows of an
asset on one handle. To distinguish this from cache capacity, six diagnostic
profiles run in fresh processes on the same frozen real source, each validating
all 64 native window checksums, counts and sums against the local pixel oracle.
Every byte result below repeats identically three times. They are diagnostic
reader workloads, not replacements for the matched complete-acquisition matrix.

| Controlled GDAL 3.10.3 profile | Source bytes | Duplicate bytes | Median process wall |
| --- | ---: | ---: | ---: |
| One reused handle, row order, 32-MiB decoded cache | 8,978,432 | 0 | 0.262 s |
| Same reader, decoded cache set to zero | 8,978,432 | 0 | 0.407 s |
| One reused handle, source-block order | 8,978,432 | 0 | 0.263 s |
| Four handles, serial round-robin windows | 8,978,432 | 0 | 0.416 s |
| Four handles, concurrent round-robin windows | 12,009,472 | 3,031,040 | 0.273 s |
| Reopen a handle for every output window | 6,045,696 | 0 | 1.055 s |

The four-handle serial/concurrent comparison establishes the effect of
concurrent independent requests for these shared source blocks. A larger decoded
cache is not the demonstrated remedy. Setting that cache to zero changes decode
cost but leaves source traffic unchanged because the compressed HTTP-range cache
still serves repeated sequential reads. Raw rows and hashes are in
[trace-ablations.json](trace-ablations.json), generated by
[cog_io_ablation.py](../../bench/cog_io_ablation.py).

Both original readers also transfer substantial unselected imagery. The range
traces show adjacent download growth into the next source block; there are no
multipart HTTP requests in these controls. GDAL documents 16-KiB range granularity,
progressively enlarged sequential downloads, and a separate process-global
16-MiB HTTP-range cache. These differ from the configured 32-MiB decoded block
cache. [GDAL virtual-file-system documentation](https://gdal.org/en/stable/user/virtual_file_systems.html#vsicurl-http-https-ftp-files-random-access).

The reopen profile reduces sequential read-ahead but costs roughly four times
the row-order process wall time. Merely traversing output windows by source block
does not reduce bytes here. Neither diagnostic justifies a new production cache,
a TIFF decoder, nor a default range-setting change. Keeping one GDAL handle per
selection is the supported narrow correction.

Overlap-A and overlap-B each intersect the same four selected compressed source
blocks per asset despite their much smaller output areas. Their differently
aligned windows trigger different sequential read-ahead ranges. The overlapping
AOIs run in independent fresh processes: there is no claimed persistent reuse
between the acquisitions.

## Candidate diagnostic and limits

The first selection-batched, two-worker candidate delivered exact scientific
results for all four frozen workloads and eliminated repeated selected native
block payload. Its four diagnostic native runs recorded:

| Workload | Source bytes | GETs | Repeated selected payload | Repeated header-range bytes |
| --- | ---: | ---: | ---: | ---: |
| many-small | 26,558,464 | 38 | 0 | 196,608 |
| several-large | 56,918,016 | 33 | 0 | 98,304 |
| overlap-A | 56,918,016 | 33 | 0 | 98,304 |
| overlap-B | 38,109,184 | 20 | 0 | 65,536 |

For several-large this removes 25.1% of original traffic and approaches the
matched GDAL byte count within 0.17%. Residual repeated ranges start at byte zero
and arise when later source headers are opened after earlier imagery has displaced
their bytes from GDAL's HTTP-range cache. Repeated overview bytes within these
header ranges remain visible; the claim is zero repeated **selected native**
payload, not zero repeated compressed imagery of any level.

The diagnostic receipt binds its exact binaries in
[trace-final-diagnostic.json](trace-final-diagnostic.json). Subsequent planning
guards and final-matrix binaries may differ; the final matched matrix is the
authority for retained performance/resource claims. These four diagnostics are
not used for elapsed-time ranking. Request bytes are source response-body bytes,
not TCP/header wire bytes. The preserved mirrors retain original COG offsets,
compression and versions, fail closed on uncaptured ranges, and do not measure
public-provider throughput.

To reaccount any final matrix without reacquiring sources:

```sh
prototype-output/zarr-env/bin/python bench/cog_io_trace.py --runs PATH/TO/runs.jsonl
```

The reusable API is `tiff_layout(path)` and
`analyze(request_records, layouts_by_source_path, workload)`. Its totals include
selected compressed bytes, repeated selected payload, repeated complete response
coverage, exact TIFF metadata, header-response bytes and request counts.
