# 01 — Ecosystem audit (Deliverable 1)

Audit date: **2026-10-09**. Versions, dates and counts were read from live repos/docs that day by nine research agents (raw notes with pinned commit SHAs and all URLs: `evidence/`). I spot-checked two load-bearing claims myself (lazycogs/async-geotiff are 100% Python by GitHub language stats; ChronoZarr v0.3.0 removed star-delta) and both held.

Evidence grades: **[SRC]** read the code/docs; **[BENCH]** reproducible benchmark (code + method available); **[CLAIM]** author/marketing assertion without reproducible method; **[INFER]** inference; **[MEAS]** a single one-off probe (not a benchmark). Tags `[N0x]` → `evidence/0x-*.md`.

---

## 0. Bottom line of the audit

1. **The primitives are mature and mostly in C.** GDAL already does range merging, parallel range fetch, multithreaded decode, overview selection, signing, retries [N04 §2]. In Rust, nothing is faster at deflate, zstd, JP2 decode or warp, and no Rust crate implements a GDAL-style warp [N07].
2. **Nothing is a Rust-native acquisition engine.** lazycogs and async-geotiff are 100% Python; only async-tiff has a Rust core and it is a reader with no windowing, resampling, scheduling or sinks [N01].
3. **The core idea already ships in Python.** Rasteret (index-first, plans all byte ranges up front, Parquet tile-offset index) and sentle (AOI+time → Zarr cube, overlap dedupe) exist and are active [N08 §A.1]. odc-stac→Zarr recipes and a closed SaaS (Wherobots RasterFlow) do the end-to-end job today.
4. **A substitution path is forming:** VirtualiZarr + virtual-tiff + Icechunk (Zarr references into COGs) and ESA's native Zarr (EOPF, operational "late 2026 or early 2027") [N08 §A.3, N05 §8].
5. **No rigorous public benchmark exists** for a *tuned* GDAL/odc-stac pipeline on Sentinel-2 L2A. Every published speedup is against an untuned or different-shaped baseline [N04 §1, §4].
6. **Genuine gaps** (shipped by no one in general form): cross-asset global read planning with a persistent layout index; adaptive per-host concurrency and hedged range reads; QA-first byte skipping; bounded-memory streaming from planner to a sink with sink-driven ordering; a zero-warp native-grid fast path; a reproducible benchmark harness [N03, N04, N07, N08].

## 2. Project cards (proven vs claimed)

### 2.1 lazycogs — `developmentseed/lazycogs` — reference only
- **License** MIT. **Language** Python only (370 KB Python by GitHub; **no Rust of its own**); depends on rustac, async-geotiff, obstore, pyproj, rasterix, xarray, pandas `[SRC pyproject]`. **Maintenance** single maintainer (hrodmn, 65 commits); 13 releases in 9 weeks, then quiet; last push 2026-08-09 (last code commit on main reported 2026-07-02); 55 stars, 14 open issues; ~440 PyPI downloads/month; Development Seed's own blog calls it "an experiment" `[CLAIM]`. [Repo](https://github.com/developmentseed/lazycogs), [blog](https://developmentseed.org/blog/2026-07-02-groundwork-05/).
- **Proven [SRC]**: discovery from a **local stac-geoparquet file only** (never a STAC API); one DuckDB `ST_Intersects` per chunk per time step through a single-worker pool ⇒ effectively serial; one asyncio task per item over all bands with a `max_concurrent_reads=32` semaphore per chunk; **no header cache across reads**; range coalescing entirely delegated to `object_store` (1 MiB/10-way, not configurable from async-geotiff); nearest-neighbour warp in pyproj+numpy; xarray lazy indexing (or dask with `chunks=`). Rasterio parity tests use one synthetic COG; cross-CRS tolerates 3 differing pixels. `explain()` dry-run plan, ordered-drain early-stop first-valid mosaic and a warp-map cache are good ideas.
- **Claims vs evidence**: README says "Rust-native stack" while warp/windowing/mosaic/orchestration are Python/numpy `[contradiction]`. Their lazycogs-vs-odc-stac notebook (init 0.77 s vs 45.5 s; 3-step subset 13.6 s vs 28.8 s) is a single laptop run, unspecified hardware/network, mismatched chunking, time grouping and dtype, outputs differ on 2 of 30 days; the init gap is "odc-stac loads every item into RAM", not a pixel-pipeline win `[BENCH, weak]`. A draft Rust-warp PR (#58) shows the numpy warp dominates wall time (e.g. `test_full_compute` 739.5→395.0 ms) on local COGs `[BENCH]`. Issue #89 (2026-08-27, unanswered) proposes merging into odc-stac/odc-loader. [PR #58](https://github.com/developmentseed/lazycogs/pull/58), [#89](https://github.com/developmentseed/lazycogs/issues/89).

### 2.2 async-tiff — `developmentseed/async-tiff` — the one viable Rust reader; reuse with upstream contributions
- **License** MIT LICENSE file, but `Cargo.toml` says "MIT OR Apache-2.0" `[contradiction]`. **Version** 0.4.0 on 2026-09-18, MSRV 1.88, pre-1.0 with breaking minors; 3 reverse crates; single dominant maintainer (Kyle Barron). [crates.io](https://crates.io/crates/async-tiff).
- **Proven [SRC @cf4bc59]**: header/IFD parsing, tile byte-range planning, per-tile decode; zero spawn/rayon/semaphore code in the Rust core; Python wheel dispatches decode to a global rayon pool. Default codecs: None, Deflate, LZW, JPEG, ZSTD; LERC/LZMA/WebP/JPEG2000 opt-in; PackBits no decoder. JP2 only as JP2-in-TIFF tag 34712 via `jpeg2k`, **no JP2 tests**; standalone `.jp2` unsupported. Tiled only (striped → "Not a tiled TIFF"), sparse tiles fail (PR #340), no 15-bit (`DataType::from_tags` returns None ⇒ **cannot read Planetary Computer's 15-bit tiles**), float16/complex unsupported. `.expect()` in LZW decoder and IFD parsing (panics; #318, #97). **Correctness bug**: planar multi-band + predictor 2/3 gives wrong pixels (#346, 2026-10-06; fix PR #348 opened 2026-10-09). Header fetch: 32 KiB prefetch, doubling; cache assumes COG layout (scattered IFDs download most of the file, #344). One `get_byte_ranges` per `fetch_tiles`; its own `ReqwestReader` has no `get_byte_ranges` override (sequential). Decode returns an owned `Vec<u8>` + cast/copy (#234, #203). Deflate via streaming `flate2::ZlibDecoder`, `Vec::new()` + `read_to_end`, miniz_oxide backend `[SRC decoder.rs:88-103]`.
- **Benchmarks**: pyasyncio-benchmark `cog_header`: 6,989 vs 285 headers/s on the same S2 COG, 500 concurrent, m5.4xlarge `[BENCH, header parsing only; blog's "25×" and the pixel-read speedup is an "expectation"]`. FOSS4G 2025 (weiji14/foss4g2025): local 272.7 MB LZW+predictor-2 S2 TCI, i5-12600HX: GDAL LiberTIFF 0.26 s at 16 threads vs async-tiff 0.45 s (**~1.7× slower**); 2.2 s vs 2.58 s at 1 thread `[BENCH, slides, not re-run]`. Blog: "just as fast as any C or C++ library" `[CLAIM, contradicted by the maintainers' own benchmark]`. Criterion benches are self-regression only. **No network pixel-throughput benchmark vs GDAL exists for any of these repos** `[N01]`.

### 2.3 async-geotiff — `developmentseed/async-geotiff` — reference only
100% Python (~2.8k LOC) over async-tiff's wheel; README lists "no resampling, no warping, no automatic overview selection" as anti-features; ignores the raster tiepoint (I,J) (`_transform.py#L46`; geotoolz#414); always fetches and decodes whole tiles and all bands. Useful for GeoTIFF semantics (nodata, masks, PixelIsPoint half-pixel shift, PROJJSON). [Repo](https://github.com/developmentseed/async-geotiff), [blog](https://developmentseed.org/async-geotiff/latest/blog/2026/02/03/introducing-async-geotiff/).

### 2.4 rustac / stac-rs — `stac-utils/rustac` — adopt types + client (raw JSON), not DuckDB path
MIT OR Apache-2.0 (GitHub shows only Apache-2.0). `stac` 0.17.6 (85k downloads), `stac-io` 0.3.4, `stac-duckdb` 0.3.13, `rustac` CLI 0.2.16, Python `rustac` 0.9.17; last push 2026-10-08; one maintainer holds 1046 of ~1250 contributions. `stac-api` is frozen at 0.8.2 (folded into `stac`/`stac-io`); GeoParquet is `stac::geoparquet` behind a feature. API client paging is **strictly serial** (follows `next` with a 4-slot prefetch); no retry by default; Python `search_to` buffers all items; **no benchmarks in either repo**. `stac-duckdb` emits `ST_Intersects(geometry, ST_GeomFromGeoJSON(?))`, ignores covering columns, errors on the `query` extension, pages by LIMIT/OFFSET, and `Client::new()` runs `INSTALL spatial/httpfs` `[SRC N02 §4–5]`. [Repo](https://github.com/stac-utils/rustac).

### 2.5 object_store / obstore / OpenDAL / AWS stack
- **`object_store`** 0.14.2 (2026-09-15), MIT/Apache-2.0, ~2 breaking minors a year. S3 (incl. Express), Azure, GCS, HTTP, local; `skip_signature`; requester-pays S3 only. `get_ranges`: 1 MiB gap, fixed 10-way parallelism, one object per call, no merged-span cap. Retry: see §1. `ClientOptions` defaults `http1_only=true`, 30 s total/5 s connect timeout; DNS is `getaddrinfo`+shuffle without cache (resolver hook added 2026-08-12); **no metrics**, the only interception seam is raw-HTTP `HttpService`; `LimitStore` is one semaphore per store, a whole `get_ranges` (up to 10 requests) takes one permit; `HttpStore` requires 206 and errors on 200. Known pain: obstore#273 (anecdotal DNS failures, 7,722/32,000), #541 credential mutex at 1,000+ concurrent requests (fixed #648, 2026-03), #104 (GCS over h2 capped ~250 MB/s vs ~1.28 GB/s h1) `[SRC/CLAIM N03]`.
- **obstore** (MIT, one maintainer; py-v0.11.1 2026-08-21): thin pyo3 wrapper, adds no scheduling. Its published benchmark (pyasyncio-benchmark) requests one hot S2 B08 object repeatedly, n=1 per cell, no CIs; my agent's re-analysis of its CSV: obstore leads 25–45% at 16–64 KiB (12.2k vs 9.1k req/s at 16 KiB); from 128 KiB up all clients saturate ~1 GB/s and obstore is equal or behind; thousands of failures at 4–8 MiB; the fsspec baseline rows have failures = requests (invalid). "Highest-throughput" and "9×/2.8×" claims are **not supported** by its own CSV `[BENCH, low–moderate rigor]`.
- **OpenDAL** 0.59.4 (Apache-2.0; five releases in five weeks): `concurrent/chunk/gap/prefetch` read options, shared `ConcurrentLimitLayer` (pluggable semaphore), process-global reqwest client, HTTP/2 not compiled by default; **S3 Express unsupported** (#6152), Azure SAS static only; its docs say to prefer HTTP/1.1 for big transfers.
- **AWS Transfer Manager for Rust** 0.3.1 (2026-10-09): "NOT recommended for production"; S3-only; whole object or one contiguous range; real hedging code (design doc), per-bucket throttle isolation; best reference design. **CRT / Mountpoint**: `mountpoint-s3-client` says unstable, not for general use; prefetcher is sequential-read oriented.
- **Rust-vs-Rust read benchmark of object_store, aws-sdk-s3, CRT and OpenDAL: none published.**

### 2.6 GDAL, odc-stac, stackstac — the incumbents
- **GDAL** 3.12.4 (owner's local version; rasterio 1.5.2 wheels bundle 3.12.2), MIT/X. Multi-range merge + `AdviseRead` async prefetch (3.7+, 100 MiB cap), multithreaded GTiff decode (3.6+), thread-safe datasets (RFC 101), overview selection, `gdal raster pipeline` (3.11+), GTI with STAC-GeoParquet (3.10), STACIT, Zarr v3 sharding (3.13). Undocumented caps and config contradictions (details in [N04 §4–5, contradictions]): `GDAL_MAX_RAW_BLOCK_CACHE_SIZE` default 10 MiB; `GDAL_HTTP_MULTIPLEX` "default YES" in docs but master no longer reads it; `GDAL_HTTP_VERSION` doc says "1.1 generally" but code leaves libcurl's default; `GDAL_INGESTED_BYTES_AT_OPEN` effectively 16 KiB. 3.12 lacks `ReadMultiRange` retry/sorting (arrived 3.13). **Tile-Ripper must beat tuned GDAL, not only odc-stac.**
- **odc-stac** (Apache-2.0, v0.5.3, 2026-07-29, active): every (source, chunk) read does `rasterio.open(..., sharing=False)` ("TODO: open file handle cache"), `VSI_CACHE` forced off during reads, no `chunks=` ⇒ `pool=None` ⇒ **serial reads** (undocumented), planning in Python binned by footprint polygon, defaults set only `EMPTY_DIR` and retries (no cache sizes, no `GDAL_NUM_THREADS`).
- **stackstac** (MIT): **effectively unmaintained** since 2024-08-10; owner said 2026-03-25 he has no plans to maintain it (#270). Thread-local dataset per thread + `WarpedVRT`, no overview reads, defaults float64.
- **rioxarray**: global read lock by default (`lock=None`→`RASTERIO_LOCK`). rio-tiler/TiTiler: tile-oriented. cogeo-mosaic: an index. xarray-spatial: analysis only. gdalcubes: same GDAL ceiling. openEO (CDSE): 2 concurrent sync jobs, "tested up to 100×100 km at 10 m". Xee/GEE: 48 MB per `computePixels` request; Community tier 40 concurrent / 100 req/s; lock-in. Sentinel Hub sync output ≤ 2500 px `[CLAIM]`.

### 2.7 Rust Zarr and sinks
- **`zarrs`** 0.23.14 (2026-08-14; MIT OR Apache-2.0): the only credible Rust Zarr v3 library (old `zarr-rs`/`rust-zarr` dead). Sharding index at end; full-shard `store_chunk` collects inner chunks in a `Vec` (source TODO: "can use a lot of memory"; issue #482 open); partial-shard writes default to read-modify-write; `supports_set_partial()` is false on object stores. All-fill chunk `store_chunk` **erases** the key. `zarrs_filesystem` 0.3.13 (2026-10-06/07) now `fsync`s every chunk write. Bus factor 1 (LDeakin 1852 commits, next 15); API churn 28–43 breaking bullets/minor; async API self-described experimental. Benchmarks (zarr_benchmarks @ 0.23.0-beta.3): local NVMe, 32 MB chunks, zstd level 0, one 8-core laptop; round trip zarrs 0.43–1.30 s vs tensorstore 1.4–1.9 s vs zarr-python 4–6.8 s; on sharded tensorstore is within 10% `[BENCH, doesn't transfer to 2 MB chunks/zstd-5/network]`.
- **Icechunk** 2.3.0 (Apache-2.0, Earthmover): Rust writes via `zarrs_icechunk`; atomic commit via conditional update of one `repo` object; **chunk keys are `chunks/<base32 id>`** so plain Zarr clients (zarrita, GDAL) can't read the repo — conflicts with ChronoZarr's static-host premise; staging-only candidate. Earthmover's S3 write benchmark: Python zarr-python with Rust storage already saturates 13 Gbps on a 15 Gbps link `[CLAIM, vendor]` ⇒ network, not codec, caps writes.
- **COG writers**: `tiff` 0.11.3 has no tiled encoder; `geotiff-writer` 0.8.1 correct COG layout but created 2026-03, one author, stages tiles in a temp file; `gdal` crate 0.19.0 mature (C++ libgdal).

## 6. Bulk-transfer tools (s5cmd, rclone, aws-cli, AzCopy, …)

Source: [N09](evidence/09-transfer-tools.md). Nothing was run against real data.

**Finding 1 — none of them can do the engine's job.** s5cmd, rclone, aws-cli (classic and CRT), AzCopy, `gcloud storage` and aria2 cannot read many spans from many objects (source grep; rclone `cat --offset/--count` is one span per process) `[SRC]`. Only `curl -Z` (`--parallel-max` default 50, per-URL `range=`) and minio/warp (`get --range`, own objects only) issue ranged GETs at scale. These tools are **whole-object comparators and bandwidth-ceiling probes**, not span baselines. Whole-object download over-fetches ~150× for a small chip, so it is a full-tile ceiling, not an AOI baseline.

**Ceilings to use for `T_io_floor` sanity** `[N09]`: AnyBlob (VLDB 2023) `[BENCH, peer-reviewed]`: per request median 55–60 MiB/s, hard cap ≈ 95 MiB/s on 16 MiB objects; aggregate median ≥ 75 Gbit/s (mostly 80–90) on c5n.18xlarge with ≤ 256 requests. CRT assumes 0.4 Gbps (≈ 50 MB/s) per connection and says its own small-object throughput is lower; for ~1.3 MB ranges my agent estimates ≈ 23 MiB/s/connection ⇒ ~54 connections for 10 Gbps `[INFER]`. EC2 single flow 5 Gbps; internet-gateway path capped at 5 Gbps below 32 vCPU; S3 5,500 GET/s per prefix. **Nobody has published ~1 MB range throughput or TTFB on EC2 in-region** — benchmark experiment E2.

**Design ideas worth copying for the scheduler:** one global in-flight budget (CRT's 4× connections, not s5cmd's workers × parts); AzCopy's one-shot hill-climb as a per-host warm-up probe (plus periodic re-probe, which it lacks); rclone's separation of request-rate token bucket from a retry pacer with shared sleep state and `Retry-After`; CRT's no-HEAD ranged first request and memory-derived part sizing; `gcloud`'s workload-shape presets.

**Comparator set S7 (see [04 §4](04-benchmarks.md)):** aws-cli with explicit CRT (`preferred_transfer_client crt`, `target_bandwidth` = NIC, `response_checksum_validation when_required` or record the extra HEAD, `--no-sign-request`, write to tmpfs) as the S3 headline; s5cmd 2.3.0 (`--no-sign-request --numworkers W run cmds.txt`, sweep W 16…256, flagged stale) as secondary; rclone (`--transfers N --checkers N --files-from --no-traverse --no-check-dest --ignore-checksum`) for cross-host; AzCopy (SAS URLs, `AUTO` vs fixed, in-region Azure VM) for PC; aria2/curl for plain HTTPS lists; `aws-crt-s3-benchmarks` (`download-max-throughput`, reproducible, publishes no results) and warp as ceiling probes. Pitfalls: aws-cli behaves differently per host; rclone's destination checks/listing add overhead; AzCopy writes plan/log files; s5cmd and aws-cli cannot use Azure SAS URLs; whether the CRT runner can make unsigned requests to `sentinel-cogs` is unverified (may need a copy in a writable us-west-2 bucket).

## 7. What this audit does **not** establish
- Network pixel throughput of async-tiff/async-geotiff/lazycogs vs GDAL (nobody has published it).
- Whether a tuned GDAL/odc-stac with `GDAL_NUM_THREADS`, a raised raw-block-cache cap, and 32+ Dask threads closes the gap to async engines (nobody swept it) — **this decides novelty**.
- GDAL 3.14's single curl run thread (help or hurt).
- Whether S2 hosts throttle at the >1000 GET/s a planner implies; S3 per-connection throughput for ~1.3 MB ranged GETs (modelled, not measured).
- hayro vs OpenJPEG on real S2 15-bit files; libdeflate vs zlib-rs on aarch64.
- Whether PC's 15-bit packing is universal and whether block layout varies by processing baseline.
