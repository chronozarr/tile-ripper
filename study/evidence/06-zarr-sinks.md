## 1. CHRONOZARR v0.3 ON-DISK LAYOUT (exact)  [SRC spec/CHRONOZARR.md; src/chronozarr/encode.py; schema.py; sample store data/adoption/extended-20261003/series/0/data/zarr.json]

Root group zarr.json: attributes.zarr_conventions = [chronozarr, multiscales(UUID d35379db-...)], attributes.chronozarr {spec_version "0.3.0", variable "data", times[ISO], bands[{name,common_name,scale,offset,units}], band_names, nodata (number|null), crs "EPSG:xxxxx", levels[{path,resolution,transform[6],shape[4],grid[2]}], mask_variable?, coverage_variable?, volatility_path?, provenance{sources,composite,gap_fill none|carry-forward,notes}, shard_bytes? (sharded only)}, attributes.multiscales {layout:[{asset:"0"},{asset:"1",derived_from:"0",transform:{scale:[2,2],translation:[0,0]}}...], resampling_method:"average"}. Consolidated metadata written into root zarr.json (zarr.consolidate_metadata; zarr-python emits ZarrUserWarning, encode.py:338-342).

Levels = groups "0","1",... consecutive. Default: stop at first level whose cell grid is 1x1 (inclusive). Example: 2765x2759 px, cs 512 -> grids 6x6,3x3,2x2,1x1 = 4 levels, 50 cells. [docs/archive/append-v02.md]
Each level group attrs: crs, transform[6], resolution (mirrors). Pixel scale doubles per level, origin fixed (scale_transform).
Each level group holds arrays:
* `data` : shape [n_time, n_band, H_k, W_k]; dtype uint8|uint16|int16|float32 (identical at all levels); dimension_names ["time","band","y","x"] AND attr _ARRAY_DIMENSIONS (identical); chunk_grid regular; **unsharded default chunk (1, n_band, cs, cs)**, cs even, default 512 (256 allowed); chunk_key_encoding default, separator "/"; keys `c/{t}/0/{r}/{c}`; fill_value = nodata if numeric else 0; codecs: bytes(little) -> one compressor: zstd {level 5, checksum false} default | blosc{cname zstd|lz4, shuffle noshuffle|shuffle, clevel 0-9, typesize=elemsize, blocksize 0} | gzip 1-9. Attrs on every data/mask/coverage array: proj:code, spatial:dimensions ["y","x"], spatial:transform, spatial:registration "pixel", spatial:transform_type "affine", spatial:shape, spatial:bbox, zarr_conventions[proj,spatial], nodata (data only, if not null), optional _CRS {url} for GDAL<3.13, crs/transform aliases. [schema.py data_array_attrs:321-349]
  * Optional sharded: shards (shard_time, n_band, cs, cs), inner (1, n_band, cs, cs), sharding_indexed, index_location "end" (zarrita 0.7.5 mis-decodes "start"), shard keys c/{ts}/0/{r}/{c}. Default shard_time = n_time at creation (if sharding chosen). Sharded = opt-in; unsharded default since 2026-10-01 because a CDN miss on the 2 KB index range pulled the whole 83-174 MB shard (CLAUDE.md). Append to sharded store rewrites trailing shard.
  * Edge chunks: stored chunk is full cs x cs; out-of-array padding must equal fill_value (spec 2.1).
* `mask` (optional, all levels or none): [n_time,H,W] uint8 0/1, fill 0, chunks (1,cs,cs), dims ["time","y","x"]; coarser = max over 2x2 (any valid).
* `coverage` (optional, all levels or none): [n_time,H,W] uint8, fill 0; spec: number of valid observations saturated at 255; coarser = (sum+2)//4 of the 4 edge-replicated source values.
* coords `time` int64 epoch ms (units "milliseconds since 1970-01-01T00:00:00", calendar proleptic_gregorian), strictly increasing, 1 chunk; `band` string (vlen-utf8 + zstd, 1 chunk) or int32; `y` float64 decreasing pixel centres; `x` float64 increasing. All carry _ARRAY_DIMENSIONS + dimension_names.
* root `volatility` (optional): float32 [grid_rows0, grid_cols0], single chunk, dims ["row","col"]; mean |x[t]-x[q(t)]|/10000 clipped [0,1], q(t)=nearest index in {0,s,2s..} (s=6, ties earlier). Only cross-time coupling left (could be post-pass).
* Scale/offset: per-band in chronozarr.bands; physical = stored*scale+offset; writers MUST NOT set CF scale_factor/add_offset.
* Nodata: single number or null; NaN forbidden; validity precedence: mask (shared across bands) > per-band sentinel compare > all valid.
* Overview math (spec section 5, _writer.py:downsample_2x): level k derived from stored level k-1 (recursive, NOT directly from level 0); pad to even by edge replication (incl. mask/coverage); valid-only block mean; uint8/uint16 sum in uint32, int16 in int32, floor division by valid count; float32 accumulate float64; no valid pixel -> nodata or 0; sentinel validity is per band, mask validity is shared. A Rust writer must reproduce this bit-exactly or stores diverge.

Time axis append (spec 8.3): only at end; new dates strictly after last; grid/bands(incl scale/offset/units)/dtype/CRS/nodata/mask/coverage presence must match; resize arrays, rewrite `time` coordinate chunk (single chunk), update chronozarr.times, levels[].shape, shard_bytes, consolidated metadata; unsharded append writes only new chunk objects; sharded append rewrites only the trailing/new time shards. Publication order: new chunks -> time coords+volatility -> descendant zarr.json -> root zarr.json last; "not atomic"; **writer MUST build the append in a working copy and validate before publication** (8.3).

## 2. WHAT THE WRITER CONSUMES TODAY (Python)  [SRC src/chronozarr/_writer.py, encode.py, append.py]

* Public: `encode(data, out, ...)` where data = xr.DataArray (time,band,y,x) OR iterable of per-timestep (band,y,x) arrays (needs times/crs/transform/bands). Optional mask/coverage planes (iterable per timestep (y,x)). dtype validated against {uint8,uint16,int16,float32}; "chronozarr never converts dtype". (_writer.py:622-692)
* **Orientation is cell-major, not frame-major.** `_Pyramid` (_writer.py:452-527) walks the *top* level cells and recurses depth-first: a level-0 cell block holds ALL timesteps `Block.data (T,B,h,w)`; level k cell assembled from the 4 child blocks downsampled over all T. Children submitted before parents. Memory per cell block = T*B*cs^2*itemsize (117 months x 4 bands x 512^2 x 2 B = 245 MB), x workers (default 4, DEFAULT_CELLS_IN_FLIGHT) plus parent assemblies. Measured peak RSS: 3.8 GB for full 117-month unsharded encode (docs/archive/append-v02.md, v0.2 era).
* If input is an iterable of per-timestep frames, `_spill_timesteps`/`_SpillSource` **transposes it to cell-major temp .bin files first** (one file per cell per variable; each timestep write = one 2 MB write per cell), then encodes cell by cell. => full extra disk copy of the raw stack. `convert.py` docstring: disk = raw stack in work dir + once more in spill + output. So today a frame-by-frame acquirer pays a transposition + temp disk round trip.
* Write call: `arrays.data[window,:,ys,xs] = out[window]` (zarr-python slice assignment; window = shard_time timesteps; for unsharded, each timestep is its own chunk; zarr-python compresses a cell's chunks in parallel).
* `workers` param = cells in flight; ThreadPoolExecutor for downsample; numpy releases GIL for most ops, zstd compress via numcodecs.
* Volatility computed in `_encode_cell` from the full-T block (only cross-time consumer).
* Append (`append.py`): `_append_in_place`: validate mismatches (grid/dtype/crs/transform/bands/mask/coverage/nodata/times), spill new frames cell-major, resize arrays, run same _Pyramid over *only new timesteps*, write [old_n:new_n] slices, rewrite time coord (overwrite=True), update `chronozarr` attrs, `zarr.consolidate_metadata`. Public `append()` = `shutil.copytree(original -> working)` (copies the ENTIRE store, append.py:546-549), run in-place on the copy, `schema.validate`, then copy changed files back (data first, root zarr.json last, `.append-part` + atomic replace). Local directories only ("append works on a local store").
* Measured (v0.2-era docs/archive/append-v02.md; 16-core Mac, 128 GB, shared load; 117 Ucayali months, 2765x2759 px x 4 bands uint16 = 61 MB/frame): fresh unsharded encode of all 117 months 41.9 s, 3.8 GB peak RSS, 6451.8 MB in 5,893 objects (zstd-5 ratio only ~1.1x: S2 monthly medians are noisy); build 115 months sharded 32.1 s / 4.7 GB RSS; append 1 month 0.55-0.7 s, 55 MB. 13-month encode 4.8 s. PNG-frame example: 36 frames 1024^2 -> read 0.5 s, encode 1.0 s (113 MB raw). => Python encode ~110-170 MB/s end to end. [SRC, docs; wall times carry ~20% noise per author]
* Upload (memory note reference_deployment.md): scripts/r2_sync.py boto3, 32 parallel puts, ~100 objects/s, ~24 MB/s from Jake's home link; wrangler ~2 objects/s.

## 3. MINIMAL "CHRONOZARR SINK CONTRACT" (derived)  [INFER from section 1-2; each constraint sourced above]

Unit of work: **(t, level-0 cell r,c)** = array [n_band, h<=cs, w<=cs] of the declared dtype (4 bands uint16 512^2 = 2 MiB), plus optional mask [h,w] uint8 (0/1) and coverage [h,w] uint8 for the same (t, cell). All bands co-registered on the single store grid (EPSG north-up, origin & pixel size fixed at creation; cell (r,c) = pixels [r*cs:(r+1)*cs, c*cs:(c+1)*cs]; row 0 north). Mixed-resolution bands (S2 10/20 m) must already be resampled by the engine. Metadata handed once: crs, transform, bands[] (name, common_name, scale, offset, units), nodata, times[] (strictly increasing, epoch-ms, known at creation or via append), cs, codec, provenance, whether mask/coverage planes exist.
Ordering rules:
1. Level 0: any order across (t, r, c) and in parallel; chunks are independent objects (unsharded). No cross-timestep dependency in v0.3 baseline.
2. Level k>0: cell (t,k,r',c') needs the four level k-1 cells (t, 2r'..2r'+1, 2c'..2c'+1) in their *stored* (already floor-divided) form; accumulator keyed by (t,k,r',c'). If arrival is row-major/Z-order, pending state per t is small (~one chunk-row of siblings per level, e.g. ~6x2 MiB for a 6-col grid). Adversarial/random arrival can make pending state unbounded.
3. Time: array shape fixed at `n_time`; time coord is a single chunk; `chronozarr.times`/`levels[].shape` must match -> either pre-size from the STAC search result or use append semantics (new t strictly after last; resize + rewrite time coord + root metadata each time). Out-of-order *timesteps* are fine for chunk writes if n_time/times known up front; append requires time order.
4. Mask/coverage: all-or-none across levels and for every appended timestep.
5. Sharded option: a shard = one cell x shard_time frames; zarrs/zarr-python need the **complete shard in memory** before write (no streaming to object storage). Time-major acquisition => must buffer shard_time x full frame (12 x 61 MB = 730 MB for Ucayali; whole-axis 117 = 7 GB) or spill; cell-major acquisition (all t for one cell, quad-tree order) gives a bounded buffer (shard_time x 2 MiB) and makes carry-forward gap-fill a local operation. Unsharded + time-major: memory = one frame + pyramid tail, independent of T (Python's cell-major approach scales with T).
6. Engine-level (not format) ordering: carry-forward gap-fill is serial in t (month t needs finalized composite t-1 per pixel); coverage should be a valid-observation count (spec 4.3).
7. Optional volatility needs q(t) which can be a *future* anchor (t=4 -> anchor 6): compute as post-pass over level-0 chunks or buffer; absent store is conforming.
8. Edge chunks must be padded to full cs x cs with fill_value (zarrs `store_chunk` requires full chunk shape: array_write_ops_array.rs:190).
9. Publication: chunks first, then coords/volatility, then descendant zarr.json, root zarr.json last (spec 8.2, 8.3). Spec requires working copy + validate for append; direct streaming to the final bucket needs a staging prefix or a reading of 8.3 that allows new immutable chunk keys to land first.
Legacy v0.2 constraints (now removed, relevant only for old stores / `convert`): anchors every `anchor_interval` (6), delta chunk t = (value - anchor[delta_reference[t]]) modulo dtype, |t-a| < interval, delta_reference immutable once published, append "references the nearest anchor that exists after the append", shard sizes were anchor multiples; unsigned dtypes only.

Contradictions inside the chronozarr repo:
* spec 4.3 says level-0 coverage = number of valid observations (saturated at 255); examples/sentinel2_pc/ingest.py stores `coverage = npz["coverage"] > 0` (0/1) and the provenance note says "coverage is 1 where at least one scene was valid ... (the monthly files store the valid fraction, not a scene count)". Not literally conforming.
* spec 8.3 "MUST construct an append in a working copy"; `append()` implements it by copying the whole store (6.4 GB for Ucayali) - the "0.55 s / 58 MB append" numbers in docs/archive/append-v02.md time the old in-place path.
* CLAUDE.md "Format decisions" still says "Every array carries dimension_names or xarray refuses"; consistent. But memory notes (star-delta, zarr-layer ndpyramid multiscales list) are v0.2 and stale.
* Sample v0.3 store written 2026-10-03 (data/adoption/extended-20261003/series/0/data/zarr.json) lacks `zarr_conventions`/`spatial:registration`/`spatial:transform_type` that HEAD's `data_array_attrs` emits => pre-final v0.3 draft writer; validator behaviour on it not checked.

* Async API maturity: Cargo feature `async` described "experimental"; lib.rs: "The async API is runtime-agnostic ... not as performant as the sync API"; array.rs:366-373: async methods "do not spawn tasks internally, so asynchronous storage calls are concurrent but not parallel", codec work still uses rayon (blocks the polling thread); `async_retrieve_chunks` doesn't parallelise over chunks. `AsyncToSyncStorageAdapter` (needs a tokio Handle block_on) is documented "This adapter has footguns". Recommended pattern for a Rust engine [INFER]: sync zarrs encode inside spawn_blocking/rayon, custom `WritableStorageTraits` impl (or object_store `put` directly) as the upload queue.
* AsyncObjectStore::set = `object_store.put(path, payload)` single atomic PUT (no multipart) [SRC zarrs_object_store/src/lib.rs:151]. Good for 0.5-2 MiB chunks; for 80-170 MB shards a single PUT works on S3/R2 (<5 GB) but holds the object in memory.
* FilesystemStore gotcha: **zarrs_filesystem 0.3.13 (released 2026-10-06/07) now calls `File::sync_all()` after every `set`/`set_partial_many`** (CHANGELOG "Fixed ... #462"; lib.rs:119, 321). std `sync_all` on macOS maps to F_FULLFSYNC -> per-chunk device flush; 5,900-50,000 files per store. Writes are open(truncate)+write in place, NOT temp+rename, so a concurrent reader (e.g. local range server) can observe torn files. A custom store or a pre-0.3.13 pin avoids the fsync [INFER on perf; behaviour itself SRC]. Note supply-chain: 0.3.13 and icechunk 2.3.0 (2026-10-06) are inside Jake's 7-day quarantine as of 2026-10-09.
* Benchmarks (https://github.com/zarrs/zarr_benchmarks @8f46e53, 2026-01-09, "zarrs 0.23.0-beta.3"): 1024^3 uint16 arrays; chunk 256^3 (32 MB), sharded inner 64^3, zstd level 0; Intel Core Ultra 7 268V 8c, 32 GB, NVMe, Arch Linux; best of 5; disk cache cleared; Python tools "may not be using an optimal API". Cooperative distributed writes: `fork` -> workers -> `Session::merge(other)` (session.rs:1612) -> single commit; uncooperative = optimistic concurrency. (understanding/parallel.md; reference/spec-v2.md). Non-goal: "Low Latency" (extra metadata indirection, spec-v2.md:44).
* **Layout is NOT plain Zarr keys**: chunks live at `$ROOT/chunks/<id>`; a plain Zarr client / zarrita / GDAL cannot read the repo without Icechunk-aware code (chunk bytes themselves are standard Zarr-encoded, "Chunk encoding and compression are defined by the Zarr specification"). This conflicts with chronozarr's core premise (static host, generic Zarr clients, deterministic keys `c/t/0/r/c`, `shard_bytes` inventory). Icechunk could be a *staging/transactional ingest sink* followed by an export that copies chunk objects to canonical keys (no re-encode) [INFER]; as the published layout it is incompatible. It would solve the problems chronozarr 8.3/8.4 concede (non-atomic multi-object append, stale shard index) at the price of the plain-layout guarantee. Earthmover's own measured chunk guidance: 3-15 MB optimal vs ChronoZarr 2 MiB unsharded chunks.
* Icechunk docs list Python/Rust/JS; no GeoTIFF/COG/spatial awareness.

## 8. VERDICT NOTES

Which crate for the Zarr sink: `zarrs` (only credible Rust Zarr v3 implementation; covers every ChronoZarr codec/dtype). Use sync API + rayon, pin exact version (=0.23.14), do not use the async API or zarrs_filesystem >= 0.3.13 for bulk writes without measuring.
Missing for ChronoZarr (to be built, ~port of Python): (a) overview/pyramid semantics (downsample_2x etc.) and mask/coverage reducers; (b) chronozarr attribute/metadata builders + conformance validator (schema.py is 1269 lines, Python only - could shell out to `chronozarr validate`); (c) consolidated-metadata assembly; (d) publication protocol/working copy/append rules; (e) bounded-memory shard writer (zarrs issue #482) and multipart sink; (f) upload scheduler with retries/backpressure; (g) STAC/`shard_bytes` inventory.
Risk of depending on zarrs: LOW for format lock-in (output is plain Zarr v3; any reader works), MEDIUM-HIGH for API churn (28-43 breaking changes per minor; 0.24 pending with 35), HIGH bus factor (one maintainer, 97% of commits; academic employer) - mitigated because the default unsharded layout is only `zstd(le_bytes)` objects + JSON metadata, so a ~200-line fallback writer (zstd crate + serde_json, crc32c for shard index) is feasible; keep the zarrs boundary behind one `encode_chunk`/`put` function [INFER]. Cross-check output against `chronozarr validate` + zarr-python/zarrita in CI.
