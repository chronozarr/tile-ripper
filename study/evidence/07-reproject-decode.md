Scope: CRS transforms, warp/resample kernels, mosaic semantics, deflate/zstd/JP2 decode, memory/SIMD/runtime.

## 0. Headline findings (decision-relevant)

1. **S2 payloads in COG form are plain DEFLATE.** [DATA] Earth Search `sentinel-2-l2a` COGs: Deflate + Predictor 2 (horizontal differencing), uint16, 1024x1024 tiles at full res (512 for overviews), mean compressed tile 1.2-1.4 MB of 2 MiB raw (ratio 1.5-1.75, 6 AOIs). Planetary Computer `sentinel-2-l2a` B04/B11 assets are now COG `.tif` (SAFE path layout): Deflate, **Predictor 1 (none)**, 512x512 tiles, **BitsPerSample = 15 (bit-packed)**. No zstd, no LZW, no LERC anywhere in S2 COGs I inspected. CDSE (`s3://eodata`) serves only JP2 (B04_10m = 109.8 MB, vs ~200 MB ES COG incl. overviews) [DATA from sibling `cd_item.json`].
2. **PC's 15-bit packed COGs are a decode landmine for Rust stacks.** async-tiff `DataType::from_tags` returns `None` for 15-bit and `Tile::decode` only fixes endianness for 9..=16 bits, no unpack -> unsupported/garbage [SRC async-tiff @cf4bc59 src/data_type.rs:75-89, src/predictor.rs:12-53, src/tile.rs:80-140]. image-tiff main has `unpack_bits` for 9-15-bit MSB-first packed samples [SRC image-tiff @3302936 src/decoder/image.rs:1090,1184,1423]; whether that is in the published 0.11.3 I did not verify. GDAL handles it (NBITS).
3. **The Rust COG decode path that exists today is naive.** async-tiff DeflateDecoder = `ZlibDecoder::new(Cursor(buf))` + `Vec::new()` + `read_to_end` (streaming, no capacity hint, no buffer reuse), on flate2 *default* backend = miniz_oxide [SRC async-tiff src/decoder.rs:88-103, Cargo.toml `flate2 = "1.0.20"`; flate2 README: default is miniz_oxide]. GDAL's libtiff uses **libdeflate** one-shot when built with it [SRC gdal @5154115 frmts/gtiff/libtiff/tif_zip.c:43-253]. libdeflate is ~2x faster than miniz_oxide flate2 [BENCH libdeflater README, 2-3x on Calgary/Canterbury] and ~1.5x faster than zlib-ng on silesia (1.1 vs 0.7 GB/s) [BENCH-ish TurboBench, 2023, Ryzen 6600HS]. => A thin libdeflater-based decoder (pre-sized pooled output buffer + fused predictor/unpack/crop) is a small, high-value, C-library-wrapping component. Rust does not win here; C does.
4. **JP2 decode is the real bottleneck for ESA originals, and Rust-native is not ready to bet on.** OpenJPEG 1024x1024 S2 tile: 127 ms on 1 thread vs 19 ms on 8 [CLAIM: commit msg 542977c in alex-s-gardner/ChunkManifests.jl PR #18; hardware unstated; no code]. => ~15 s/band/tile single-threaded (121 tiles). Vs deflate tile ~3-6 ms [INFER] -> JP2 is ~20-40x more CPU per tile. `hayro-jpeg2000` is the only credible pure-Rust JP2 decoder (see sec 3.4) but: whole-image decode API only, no threading, no ROI/tile-selective API, f32 sample containers, README says "worse performance than OpenJPEG", a **lossless bit-exactness bug was fixed only in 2026-07** (#1283). The "native" JP2 decoders in AI-written mega-crates (OxiGeo, Whitebox wbraster) have documented history of corrupt output on real Sentinel JP2s (sec 3.5).
5. **S2 JP2 originals (most likely baseline N05.12: same tile 17SPV / 2026-08-30 as the N05.12 PC/ES items; the file itself does not state its baseline) are lossless 5/3, 15-bit, 4 DWT levels, 1024 tiles, 64x64 codeblocks, precincts 256, LRCP, 1 layer, TLM present, written by Kakadu v7.4.** [DATA: parsed SIZ/COD/QCD/TLM/COM from the first 8 KiB of an S2 L2A 10 m B04 JP2 (EPSG:32617, tile 17SPV; sibling file `aws_B04.jp2hdr`)]. TLM exists -> OpenJPEG >= 2.5.3 can range-read only needed tiles (Kayrros: crop 4.3 s/110 reqs without TLM vs 0.39 s/3 reqs with [CLAIM-with-script: Kayrros/sentinel-2-jp2-tlm benchmark.sh]). Reversible 5/3 means integer-exact path; the "lossy decode is 0.6-2.1 dB worse" hayro caveat does not apply, but #1283 (lossless LSB bug) did.
6. **No Rust crate implements a full GDAL-style warp.** Closest: `rwarp` (3.2k LOC, MIT/Apache, single author, 48 downloads, 4 kernels, no threads/SIMD, no mosaic/average/mode) and `wbraster` (in-memory, exact per-pixel PROJ-like transform, 10 resample methods, rayon over rows; whole-raster `Raster`, `Option<f64>` per pixel). `warp-rs` (2026-10-05) is an affine-only stub ("Nothing warps yet"). georust `gdal` exposes only `reproject()` hardcoded to bilinear, but `gdal-sys` exports the whole C warp API incl. `GDALWarp`, `GDALWarpRegionToBuffer`, `GDALChunkAndWarpMulti`, `GDALCreateApproxTransformer`.
7. **The "zero-warp" S2 fast path has Python prior art to copy, not Rust prior art.** `odc.geo.overlap.compute_reproject_roi` -> `paste_ok` when dst->src affine is pure integer-scale + integer translation (translation tol 0.05 px, scale tol 1e-3) and `read_shrink` picks an overview; `odc-loader` then `rdr.read(window=...)` directly into the destination slice, no warp [SRC odc-geo @da697a6 odc/geo/overlap.py:362-400,424-545; odc-loader @38395b1 src/odc/loader/_rio.py:478]. GDAL itself has **no** identity/memcpy kernel (grep of gdalwarpkernel.cpp: none); for same-CRS it keeps source resolution but still runs the per-pixel nearest kernel.
8. **CRS-transform speed is irrelevant if you use the approximate-transformer trick; CRS-transform *correctness scope* is what matters.** For S2 (WGS84/UTM, 4326, 3857, polar stereo) pure-Rust proj4rs / proj-core cover the math. Per-point exact cost is ~40-130 ns (UTM; M1) so a 1024^2 tile exact = 40-136 ms, but with a 0.125 px error-bounded linear approximation only a handful of points per scanline are transformed.

### 1.1 `proj` crate (georust/proj) - bindings to C PROJ
- v0.31.0 (2025-08-29), MIT/Apache-2.0, 850k total dl, tracks PROJ 9.6.2 [crates.io; SRC https://github.com/georust/proj/blob/a67b941e8f6f6cd54c4b9295d1beeb174f8e1c6f/CHANGES.md]. PROJ itself is MIT.

PROJ C API exposes "threading contexts" (`proj_context_create`, `proj_context_clone` added 7.2) [SRC https://proj.org/en/stable/development/reference/functions.html]; as one example of internal state mutation, PROJ 9.6 `proj_factors` on a projected-CRS P object "will no longer" support concurrent calls on the same P. (I did not find a single general PROJ-docs sentence on PJ thread-safety; the georust comment above is the operative rule.) => rayon `map_init`/thread_local per-worker `Proj`.
- API: `convert_array`/`project_array` allocate (TODO comment: PJ_COORD vs Coord<T> size mismatch, proj.rs:1074,1105), `transform_bounds` with edge densification exists (bbox -> source window planning) [SRC proj.rs ~1120+].

## 2. Resampling / warping

### 2.1 GDAL warp = the performance reference [SRC gdal @5154115825852ee99091b939886d3f24bddb10bd]
- `-et` error threshold default **0.125 source px**; `-et 0` disables approximation [doc/source/programs/gdalwarp.rst:197-202; apps/gdalwarp_lib.cpp:1372]. Approx used unless threshold 0 [gdalwarp_lib.cpp:2990-2997].
- `-wm` warp memory default **64 MB** (GDALWarpOperation default 64*1024*1024, alg/gdalwarpoperation.cpp:611-613); shared among threads; destination split into chunks when `dfTotalMemoryUse > dfWarpMemoryLimit` (gdalwarpoperation.cpp:1553); `OPTIMIZE_SIZE` reshapes chunks to align with output blocks, may slow warp (gdalwarp.rst:720-722).
- `-multi` = 2 threads overlapping I/O and compute; compute parallelism only via `-wo NUM_THREADS=n|ALL_CPUS` (gdalwarp.rst:387-393); `GWKThreadsCreate` uses `GDALGetNumThreads(..., "NUM_THREADS", ..., bDefaultAllCPUs=false)` -> off unless set (gdalwarpkernel.cpp:311-330). Row-block jobs on a global thread pool.
- SIMD: SSE2 (128-bit `XMMReg4Double`) in the generic Lanczos-like `GWKResampleNoMasks_SSE2_T` (Byte/Int16/UInt16/Float) and 6-tap cubic path; SSE4.1/NEON for some loads; **no explicit AVX2** (rg: only `__SSE4_1__`/`__AVX__` guards); cubic SSE variant deliberately not enabled ("gives zero" gain, line 3414-3416).
- Fast-path dispatch (gdalwarpkernel.cpp:1340-1470): specialised kernels only for NN/bilinear/cubic/cubicspline on UInt8/Int16/UInt16/Float32 **without masks**; with nodata/alpha masks UInt16 NN has `GWKNearestUnsignedShort`, other resamplers fall to `GWKRealCase`; `USE_GENERAL_CASE` forces the slow path. Docs: "fastest situations are nearest neighbour resampling on 8bit data without nodata or alpha masking" (gdalwarp.rst:~705-710). Algorithms: Nearest, Bilinear, Cubic, CubicSpline, Lanczos, Average, RMS, Mode, Max, Min, Med, Q1, Q3, Sum.
- `SRC_COORD_PRECISION` (default 0=off) snaps source coords to a lattice, with fallback to exact transform in the uncertainty zone (gdalwarpkernel.cpp:5202-5245) -> **bit-exact parity with GDAL on tie cases (e.g. 10 m -> 20 m where dst centres sit on src pixel edges) is fragile in any reimplementation** [INFER].
- No identity/same-CRS memcpy kernel (rg found none in gdalwarpkernel.cpp). Same-CRS only preserves resolution when computing the suggested output (gdalwarp_lib.cpp:4094-4140).
- I/O: GDAL reads via the dataset block cache (`GDAL_CACHEMAX`); JP2OpenJPEG: tile-level threading via `GDAL_NUM_THREADS` (default ALL_CPUS) and code-block threading via `OPJ_NUM_THREADS` [SRC doc/source/drivers/raster/jp2openjpeg.rst:60-81].

### 2.2 The five S2 cases -> what the engine must do
| Case | Needed op | GDAL does | Fast path in Rust? |
|---|---|---|---|
| Output CRS == S2 UTM zone, aligned to native grid | copy a window of decoded tiles into dst; no transform at all | runs NN kernel per pixel | **must be a memcpy-style tile paste** (to write; ~100-300 LOC + nodata fill). odc `paste_ok` is the spec |
| Same CRS, different origin (integer px shift) | same paste, offset | NN kernel | same code path, shifted window |
| Same CRS, sub-pixel shift (< tol) | snap (odc: ttol 0.05 px) or true bilinear | resamples | policy decision; odc snaps |
| 20 m -> 10 m (or 10 -> 20, 60 -> 10) | integer-ratio NN/bilinear (separable, axis aligned, no CRS) | warp kernel | `fast_image_resize` supports U8/U16/F32 SIMD (SSE4.1/AVX2/NEON), crop-box offsets, rayon; Ryzen 5950X L16 4928x3279 -> 852x567: Nearest 0.17 ms, Bilinear 7.7 ms (SSE4.1), vs `image` 60.9 ms [BENCH, repo benchmarks-x86_64.md @ce36aeb]; but it is a *resizer* (no nodata/mask semantics, centre convention must be matched to GDAL's). NN 2x upsample (SCL 20 m -> 10 m) is a trivial loop |
| Different UTM zone / 4326 / 3857 / polar | true warp (approx transformer + kernel) | gdalwarp | write NN/bilinear kernel on top of rwarp-style planner (see 1.5), or call GDAL C via gdal-sys |

### 2.5 Mosaic semantics in prior art
- lazycogs `_mosaic_methods.py` (ported from rio-tiler, MIT; pure numpy masked arrays `(bands,h,w)`): **First** (first valid wins, "first-on-top"), **Highest**, **Lowest**, **Mean**, **Median**, **Stdev**, **Count**; masked = nodata; pixel masked only when *all* bands equal nodata; `is_done` early-exit once every pixel is valid [SRC].
- odc-loader default fuser = "only fill where dst is nodata" (first valid wins, order = group order), custom fuser callback `(dst, src)->None`; grouping (e.g. `solar_day`) is done upstream in odc-stac [SRC odc-loader @38395b1 _fuser.py].
- Cloud masking with SCL is *not* part of either mosaic method: callers mask SCL classes (ESA: 0 nodata, 1 saturated, 3 cloud shadow, 8/9 cloud med/high, 10 cirrus; 11 snow - [CLAIM from ESA docs, not re-verified]) before/while fusing. SCL is 20 m uint8 -> NN-upsample to 10 m. For a Rust engine this is a lookup-table bitmask + `where` select, trivial; Median/percentile over N scenes needs N x tile memory (N=100, 1024^2 u16 = 200 MB/tile) or approximate streaming quantiles.

### 3.1 What S2 COGs actually use [DATA]
| Provider/asset | Compression | Predictor | Tile | Bits | Comp. ratio (vs 16-bit raw) |
|---|---|---|---|---|---|

| Planetary Computer B04, B11 | Deflate | 1 (none) | 512 (all levels; 484 tiles at 10 m) | **15 packed** | ~1.2 (423 KB per 512^2 tile) |
| CDSE `eodata` | JPEG 2000 (no COG) | - | 1024 codestream tiles (121) | 15 | B04_10m 109.8 MB |
Deflate on ratio-1.5 data is Huffman/literal heavy, not match-copy heavy -> throughput in output-MB/s is below the text-corpus numbers below [INFER]. No public decode MB/s measured on S2-like u16+predictor tiles exists that I could find.

### 3.2 DEFLATE: Rust vs C
- Candidates: `flate2` backends (miniz_oxide default; `zlib-rs`; zlib-ng via libz-ng-sys; zlib via libz-sys), `libdeflater` 1.26.1 (C libdeflate 1.26, 2026-08-22; Apache-2.0 wrapper/MIT lib; one-shot only), `zune-inflate` 0.2.54 (2023, libdeflate-style pure Rust, stale), `zenflate` 0.4 (AGPL-3.0 or commercial - license-blocked), `fdeflate` (PNG-specialised).
- **libdeflate vs zlib family (C, whole buffer):** TurboBench silesia.tar, Ryzen 6600HS, decode MB/s: libdeflate 1076-1134; zlib-ng 695-735; zlib 449-484 [BENCH-ish, third-party, 2023; https://github.com/zlib-ng/zlib-ng/discussions/2351].
- **libdeflater vs flate2(miniz_oxide):** decode 1.4-3.7x faster, avg ~2x, Calgary/Canterbury, single thread, repo-included scripts [BENCH; https://github.com/libdeflater/libdeflater/blob/260e1e9a333e32e769855c1ad1f203289e0a3c8d/README.md]. Note: it compares to miniz_oxide, not zlib-rs.
- **zlib-rs** (Trifecta, v0.6.8 2026-09-15, Zlib license; adopted by Firefox 151 for gzip, 2026-06-16): claims decompression faster than zlib-ng by >10% at 1 KB and >6% at 64 KB chunks and faster than zlib-chromium for chunk >= 2^7 on silesia-small.tar [CLAIM w/ method; blog https://trifectatech.org/blog/zlib-rs-is-faster-than-c/; code in repo `zlib_benchmarks.json`]. Earlier (2024) it was 4.8% *slower* than zlib-ng decompression [blog "current-zlib-rs-performance"]. An independent user (mxmlnkn, 2025) found it "about as fast as other perf-focused C forks, ~3x stock zlib". **No public head-to-head vs libdeflate** (repo never mentions libdeflate: `rg -i libdeflate` empty; ROADMAP goal = "competitive with zlib-ng") [SRC zlib-rs @7909c0f]. => [INFER] zlib-rs ~= zlib-ng ~= 0.6-0.7x libdeflate for one-shot inflate on x86; aarch64/macOS speedups smaller because Apple zlib uses inline asm (Trifecta Firefox post).
- **flate2 pitfall:** flate2 >= 1.1.10 gates zlib-rs's runtime CPU detection behind a *default* feature `runtime_detection`; `default-features = false` + `zlib-rs` silently loses SSE4.2/AVX2 dispatch (reported ~3x slower gzip decompress downstream) [SRC flate2 README "Backends"; derodero24/comprs#646]. geotiff-rust (roteiro-gis) declares exactly `default-features=false, features=["zlib-rs"]` with `flate2 = "1.0.35"` [SRC tiff-reader/Cargo.toml:22] - affected only if the resolved flate2 is >= 1.1.10 (check Cargo.lock).
- Also: libdeflate needs the **output size** (known for TIFF tiles: tilew*tileh*bytes) and whole compressed tile in memory - fits COG tile reads perfectly (GDAL does exactly this).
- **Verdict:** C libdeflate (via `libdeflater`) wins single-thread one-shot inflate; zlib-rs is the best Rust choice if "no C toolchain" is a hard constraint (~30-40% slower [INFER]); miniz_oxide (the flate2 default, used by async-tiff/image-tiff) is the slowest (~2x).

### 3.3 TIFF predictor, LZW, LERC, zstd, bit unpacking
- **Predictor 2 (horizontal differencing)** = per-row prefix sum with wrapping add. async-tiff: scalar byte-slice loop with per-element `try_into().unwrap()` after a separate endianness pass [SRC predictor.rs:56-95]. libtiff master: scalar `horAcc8/16/32/64`, **no SIMD** [SRC libtiff `tif_predict.c` (gitlab master, grep: no SSE/AVX)]. So C has no advantage; SIMD prefix-sum (log-step shifts within 8x u16 lanes + carry) could be ~3-6x faster than scalar [INFER] but it's ~1-2 ms per 1 Mi samples scalar vs 3-6 ms inflate -> worth a fused kernel, not a library. No Rust crate for it found (crates.io searches "tiff predictor", "delta decode simd", "prefix sum simd": none relevant).
- **15-bit unpack** (PC): MSB-first bit-unpack; `image-tiff` main implements; `bitpacking` crate is LSB-oriented integer codec, not applicable [INFER]. ~50 LOC SIMD/scalar.
- **LZW:** `weezl` 0.2.1 (image-rs, safe, MIT/Apache, 154M dl); no published MB/s in README; not used by S2.
- **LERC:** `lerc` 0.2.1 = safe wrapper over Esri C++ (`lerc-sys`, vendored); a separate pure-Rust `lerc-core/lerc-reader 0.4.2` is used by geotiff-rust. Not S2-relevant.
- **zstd:** C zstd 1.5.7 -1: ratio 2.896, **1550 MB/s decode** (i7-9700K, lzbench, in-memory; vs zlib 1.3.1 -1 390 MB/s) [BENCH-ish, upstream README]. Rust: `zstd` 0.14.1 / `zstd-safe` 8.1.0 = C binding (BSD-3, builds bundled libzstd via cc). Pure-Rust: `ruzstd` 0.9.0 (MIT): own README says decode is ~3.5x slower than C on enwik9, ~1.4x slower on incompressible ISO [CLAIM, `time`-based]; `zrip` (paddor, 2026-06; MIT; ~13k SLOC; image-tiff `zstd-safe-rust` feature uses `zrip-decode`): charts only (i7-8700B, "pipeline @100MB/s", C libzstd 1.5.7 vs zrip vs ruzstd; no numeric table; "fastest pure-Rust") [CLAIM]; the image-tiff feature comment says "somewhat slower Zstd decoding". => For the **output/Zarr side** (zstd-compressed chunks) C zstd wins by 1.4-3.5x on decode and the encode side is where ruzstd/zrip are weakest (levels <=4 only in zrip, ruzstd only "Fastest" real level). Use `zstd` crate.

### 3.4 JPEG 2000 (ESA originals)
- **OpenJPEG** 2.5.4 (2025-09-20; BSD-2). `openjpeg-sys` 1.0.12 vendors v2.5.3 exactly (git compare identical) -> includes TLM-aware partial decode (new in 2.5.3 per Kayrros). `jpeg2k` 0.10.1 (MIT/Apache; last commit 2025-07-29): exposes `DecodeParameters::reduce(n)` (skip top n DWT levels), `decode_area`, and `threads` feature -> `opj_codec_set_threads(num_cpus)` [SRC jpeg2k @74aaa2f src/codec.rs:57-120,416]. Note oversubscription if you also parallelise tiles (set threads=1 or use your pool).
- **GDAL JP2OpenJPEG** perf reputation: slow cold start on S2 over network: GDAL issue #14516 (2026-05): full-scene TCI overview from CDSE with OpenJPEG+TLM: "7-10 s on the first request", many sequential range requests, no efficient coalescing; file = 10980^2 RGB, 121 codestream tiles, TLM 728 B, 4 DWT overviews [SRC https://github.com/OSGeo/gdal/issues/14516; GDAL master 3.14.0dev]. Kayrros TLM study above.
- **Kakadu:** proprietary; GDAL docs: "not free... builder must acquire a license" [SRC jp2kak.rst]. Fastest CPU decoder at high thread counts but *slower than OpenJPEG single-thread* on Fastvideo's lossless tests (4K lossless 1T: OpenJPEG 673 ms vs Kakadu 1562 ms; 32T: 90 vs 139 ms) - vendor benchmark (Fastvideo sells a GPU codec), Ryzen 9 7950X, 24-bit RGB, OpenJPEG 2.5.2/Kakadu 7.10.2 [CLAIM, https://www.fastcompression.com/benchmarks/decoder-benchmarks-j2k.htm]. Different (older, 2016) and IIIF/HTJ2K evals say Kakadu 10-15x faster than OpenJPEG on lossy/lossless [CLAIM; code4lib/merovingio] - contradictory; workload dependent.
- **Grok** (AGPL-3.0; GDAL JP2Grok driver added in GDAL 3.13): README (16 threads, GDAL release build, Fedora 42): Spot 6 local 26.9 s vs OpenJPEG 52.1 s vs Kakadu 30.6 s; network 35.2/85/344 s; Pleiades region 0.74/4.28/1.41 s [CLAIM, unexplained method]. GDAL #14516 shows JP2Grok overview-decode over vsicurl returned wrong data (bug, closed).
- **hayro-jpeg2000** 0.4.1 (2026-10-04; Apache-2.0 OR MIT; LaurenzV/hayro, Typst/Linebender lineage; 3.6M dl, driven by PDF use; ~6.8k LOC in j2c/) [SRC https://github.com/LaurenzV/hayro/tree/9016f891986f290b9bc00dabf3e5e572c6e1cdb2/hayro-jpeg2000]:
  - README: "yields a simple 8-bit image"; but `DecodedImage::components()` exposes `ComponentData::samples() -> &[f32]` + `bit_depth()` so 15/16-bit is reachable (as f32; exact for <=24 bits) - **not exercised by its tests** (tests render PNG snapshots; corpus = OpenJPEG conformance + 20k PDF images) [SRC TESTS.md, lib.rs:193-260,380].
  - **Single-threaded** (no rayon), `fearless_simd` SIMD default-on, `target_resolution` hint for reduced-resolution decode, whole-image `Image::new(&[u8])` API: no ROI/tile-selective decode, no byte-range streaming. To use TLM you would synthesise a codestream (main header + chosen SOT tile-parts) yourself [INFER].
  - Perf: README "worse performance than OpenJPEG, but the gap should not be too large" [CLAIM]; third-party (nist_view PR #2, 0.4.0, no hardware/sizes): "speed equal to OpenJPEG", memory ~2x (13 B/px grey, 30 B/px RGB), lossless identical to OpenJPEG incl. 12/16-bit, lossy 0.06-0.5% samples differ by 1 [CLAIM]. slopshop PR #60: 4000x3000 in 1.6 s lossless single-thread [CLAIM].
  - **Correctness history:** #1283 (fixed 2026-07): truncated code-blocks reconstructed biased to zero -> *lossless 16-bit not bit-exact* (75.5% exact on a DICOM test; OpenJPEG exact). Open: #1041 "unsupported marker", #924 HTJ2K unsupported, #1052 no cancellation. Fuzz panics were fixed 2025-12.
  - => Plausible OpenJPEG replacement for lossless S2 *if* you add (a) a tile-parts/TLM front-end, (b) rayon over codestream tiles, (c) a bit-exact regression suite against OpenJPEG on real S2 L2A files. None of that exists; I found no S2-specific validation.
- Other pure-Rust JP2 crates: `pdfluent-jpeg2000` (hayro fork/rename, 0.4.0), `oxideav-jpeg2000` 0.0.17 (MIT, Part-1 + HTJ2K enc/dec, v0.0.x), `justjp2` 0.1.1, `ndic-*` (HTJ2K), `dicom-toolkit-jpeg2000` (native-bit-depth decode), `oxigeo-jpeg2000`, `wbraster` native core (known-corrupt on S2, see recovery plan). HTJ2K is irrelevant to S2 (Part-1 codestreams).
- JP2 per-tile cost: 127 ms / 1024^2 / 1 thread (OpenJPEG) [CLAIM above] vs deflate ~3-6 ms [INFER]; 8 threads: 19 ms.
- **Where C still clearly beats Rust today:** (1) one-shot inflate (libdeflate vs everything Rust, ~1.3x over zlib-rs/zlib-ng class, ~2x over miniz_oxide); (2) zstd decode (C 1.4-3.5x per ruzstd's own README); (3) JP2 (OpenJPEG >= hayro per author; Kakadu/Grok faster still, both license-encumbered; OpenJPEG is the only permissive, TLM-aware, multithreaded, region/reduce-capable decoder); (4) GDAL's warp driver (threads, SSE2, memory-bounded chunking, 14 resamplers) - no Rust peer; (5) PROJ breadth (proj.db operation selection, grids, WKT) - irrelevant for WGS84/UTM.
- Where Rust is plausibly *ahead or equal*: per-point projection math for common CRSs (proj-core 1.7-3.3x faster than C PROJ per call, M1, [BENCH]); orchestration (rayon, async I/O, buffer pooling, fused passes); build/cross-compile/WASM.

## 4. Memory / layout / compute / runtime

- **Layout:** flat `Vec<u16>`/`&mut [u16]` + (stride, w, h) newtype per tile for the hot path; `ndarray` 0.17 (130M dl) only at API edges (async-tiff has an optional `ndarray` feature; geotiff-reader returns `ArrayD`). ndarray's strided iteration is fine for zero-copy views but invites accidental non-contiguous copies and hampers SIMD autovectorisation in the copy/shift kernels [INFER].
- **SIMD options (stable Rust):** `std::simd` is still unstable as of 2026-08 (tracking issue rust-lang/rust#86656 open, label needs-rfc) [SRC]. Stable choices: `wide` 1.7.1 (Zlib/Apache/MIT; used by wbprojection), `pulp` 0.22.3 (runtime multiversioning, MIT; faer's), `fearless_simd` (Linebender; used by hayro, `forbid(unsafe)` option), raw `std::arch` + `multiversion`. `faer` is dense linear algebra (irrelevant). Prefer runtime dispatch (x86 AVX2 + aarch64 NEON) - the same pitfall as flate2's `runtime_detection`.
- **rayon vs tokio blocking pool** [SRC tokio docs "CPU-bound tasks and blocking code" https://docs.rs/tokio/latest/tokio/index.html#cpu-bound-tasks-and-blocking-code]: tokio core threads = #cores for async; `spawn_blocking` pool limit "very large" (~500, per Ryhl); for CPU-bound code "use a separate thread pool dedicated to CPU bound tasks... such as rayon"; an extra Tokio runtime works but IO tasks on it "behave poorly". Ryhl: rule of thumb <=10-100 us between `.await`s; pair `rayon::spawn` with a `tokio::sync::oneshot` [SRC https://ryhl.io/blog/async-what-is-blocking/]. Reference implementation in the ecosystem: async-tiff's own bench fetches compressed tiles async then decodes in a 4-thread rayon pool `pool.install(|| tiles.into_par_iter().map(decode))` [SRC async-tiff @cf4bc59 benches/read_tiff.rs:76-91]. Pitfalls: (a) calling `par_iter` inside an async task blocks that tokio worker; (b) `spawn_blocking` for multi-ms decode oversubscribes cores; (c) GDAL's own pools (`GDAL_NUM_THREADS`, `OPJ_NUM_THREADS`, `NUM_THREADS`) stack on top of yours -> set them to 1 when you own parallelism; (d) PROJ `Proj` per rayon worker (`map_init`/thread_local); (e) bounded channel between fetch and decode so a fast network can't blow memory (compressed JP2 tiles + 600 MB OpenJPEG scratch per decode per GDAL docs).
- **Buffers/allocators:** per-tile decode buffers are 0.5-2 MiB (u16 1024^2 = 2 MiB). glibc `M_MMAP_THRESHOLD` default 128 KiB, dynamic up to 4*1024*1024*8 = 32 MiB on 64-bit, trim threshold follows [SRC man7 mallopt(3)] -> after warm-up 2 MiB buffers come from the heap but multi-thread arenas fragment; recommended: a per-worker pool of `Vec<u8>` scratch (decode target, predictor in-place, unpack target) reused across tiles; avoid zero-filling output buffers (`Vec::with_capacity` + libdeflate writes). `bumpalo` is for many small short-lived objects (planner/metadata), not for 2 MiB tile buffers. mimalloc 0.1.52 / tikv-jemallocator 0.7.0 are drop-in for contention; **libdeflater has `use_rust_alloc`** so its allocations (decompressor state ~ tens of KiB) follow your global allocator [SRC libdeflater Cargo.toml]. async-tiff currently allocates a fresh `Vec` per tile (growth by doubling) [SRC].

## 5. Cost model for S2 (all [INFER] unless tagged)
Per 1024^2 u16 tile (2 MiB raw): network GET of 1.2-1.4 MB (ES COG) = latency-dominated (tens of ms, 100-300 MB/s/connection); inflate (libdeflate) ~3-6 ms; predictor ~1-2 ms scalar (0.2-0.4 SIMD); paste ~0.1-0.3 ms (memcpy-bound); PC variant adds 15-bit unpack ~0.5-1 ms. JP2: ~127 ms (OpenJPEG 1T, [CLAIM]). Approx-warp NN of a 1024^2 dst: dominated by gather/memory not transform. Therefore:
- COG-deflate path: **I/O and request strategy dominate; decode is second-order**; decode only matters at 16-64 core throughput or for hundreds of dates.
- JP2 path: **decode CPU dominates** (20-40x deflate); parallel tile decode + reduce/region decode + TLM range reads matter most; this is where a Rust-native decoder (if it matched OpenJPEG) or Kakadu/Grok would change end-to-end time.

### What must be written from scratch (no good existing Rust)
1. Zero-warp paste/shift fast path + planner glue (odc-geo logic as spec).
2. u16/u8 NN and bilinear kernels with nodata + SCL mask handling on top of rwarp's planner/approx transformer (or fork rwarp); downsample antialias scaling if you go beyond NN.
3. Mosaic accumulators (first/last/min/max/mean/median/count) with masks.
4. libdeflate-based tile decoder with pooled buffers and a fused predictor/15-bit-unpack/crop pass (SIMD).
5. JP2: TLM-aware range-to-codestream assembler + tile-parallel OpenJPEG (or hayro) decode; conformance suite on real S2 JP2s.
6. A parity harness vs GDAL/PROJ (bit-exact for NN; tolerance for interpolated) - none of the Rust crates ship one at S2 scale.

### Contradictions / tensions found
- zlib-rs "faster than C" (vs zlib-ng/chromium, streaming API, silesia-small) vs libdeflate being ~1.5x faster than zlib-ng one-shot (TurboBench 2023): different comparators; no libdeflate vs zlib-rs measurement exists publicly. Earlier zlib-rs blog (2024) showed it *slower* than zlib-ng at decompress (-4.8%).
- hayro: README "worse than OpenJPEG" vs third-party "equal to OpenJPEG" (no hardware, no sizes) vs #1283 showing lossless not bit-exact until 2026-07.
- Kakadu vs OpenJPEG: Fastvideo (OpenJPEG 1T faster than Kakadu 1T on lossless) vs IIIF/HTJ2K evals (Kakadu 10-15x faster). Vendor/workload-dependent.
- rwarp "bit-identical to GDAL" vs its own documented downsample-kernel divergence (4.5:1 bilinear differs) and a validation base of one 256x256 tile + GEBCO windows.
- OxiGeo advertises production JP2/warp across 75 crates; its own code contains a note about a removed grey placeholder decoder; sibling project wbraster documents corrupt S2 JP2 decode in its native path.
- Provider facts: Planetary Computer S2 B04 is 15-bit *packed* with no predictor, while Earth Search is 16-bit + predictor 2 - the same "S2 COG" label hides two different decode paths.
- sentinel-2-jp2-tlm README (2024) says S2 JP2s lack TLM; the 2026 file I parsed (baseline 05.12) has TLM. Older baselines (<05.12) still lack it.

### Open questions
1. Does `hayro-jpeg2000` 0.4.1 decode real S2 L2A 15-bit lossless JP2s bit-exactly vs OpenJPEG 2.5.3, and at what 1T/8T ms per 1024^2 tile (vs OpenJPEG 127 ms/19 ms claim)? Needs a bench on real files.
2. libdeflate vs zlib-rs one-shot throughput on S2-like data (u16, predictor 2, ratio ~1.5): needs a bench; also aarch64/macOS.
3. Is image-tiff's 9-15-bit unpack in a published release (0.11.x) or only main? Is PC's 15-bit-packed layout universal across PC S2 items/bands?
4. What did GDAL actually take per tile on S2 u16 with nodata=0 in NN (masked path) vs a purpose-built kernel? No public numbers; GDAL warp throughput (Mpx/s) is undocumented.
5. Can OpenJPEG 2.5.3 decode from caller-supplied byte ranges (custom `opj_stream`) without whole-file buffering, efficiently, while keeping the TLM benefit? GDAL issue #14516 suggests the stock GDAL path does not coalesce.
6. proj4rs vs PROJ numeric agreement on WGS84/UTM, 3857, 3031/3413 at corpus scale (none published; proj-core ships 161-value parity only).
7. ESA baseline coverage: share of the archive with TLM (>=05.12) vs without; affects JP2 random access across history.
