## 0. Bottom line (decision-relevant)

1. Nothing found that implements a true cross-asset "global read planner" for rasters (dedupe + sort + coalesce across objects + priority/deadline + hedging + adaptive concurrency + overlap with decode/write). The closest partial implementations:
   - Rasteret plans all byte ranges for all timesteps up front and dispatches them in a single asyncio.gather with one shared semaphore, but coalesces per URL only (1 KiB gap), in sequential batches of 20 ranges per URL, no dedupe, no priorities, no hedging. [SRC]
   - cptkirk (Rust+R) runs every (tile, COG-tile) fetch+decode for all sources through ONE global buffer_unordered pool, and explicitly chose NOT to coalesce (its benchmark: coalescing was slower, 66 s vs 48 s, planar 64-band layout). [SRC code comment; CLAIM for the number]
   - sentle dedupes overlapping Sentinel-2 MGRS footprints before reading (request counts 408 -> 94 in a synthetic 4-tile/2-zone case; 568 -> 240 blob requests and 2-4x faster in the real 30 km chunk run). [SRC commit + CLAIM release note]
2. The "(AOI, time, collection, bands) -> pixels fast" idea is already implemented in Python by Rasteret (index-first: tile offsets cached in Parquet, async obstore range reads, thread-pool decode, numpy/xarray/GeoPandas out). Claims 8-21x vs sequential TorchGeo/rasterio and ~8x vs thread-pooled rasterio. It lacks: Rust-native, Zarr writer, reprojection in the hot path (uses rasterio), cross-asset planner, hedging. [SRC + CLAIM]
3. "(AOI, time) -> Zarr cube" already exists: sentle (Python/GDAL/joblib, S1+S2, MIT, active), Wherobots RasterFlow (closed SaaS, GTI + Ray -> Zarr mosaics, 150 TB Zarr), Earthmover's odc-stac + serverless fan-out recipe. [SRC]
4. The "don't acquire, reference" paradigm is real and well-backed: VirtualiZarr + virtual-tiff (async-tiff based, Zarr v3, predictor-2 codec) + Icechunk; ESA EOPF Zarr (S2 as Zarr natively, operational expected late 2026/early 2027). Limits: stitch-not-mosaic, no reprojection, per-tile GETs without cross-tile coalescing (Icechunk) and zarr-python default async.concurrency=10. No public virtual-Icechunk S2 archive found. [SRC]
5. Part B verdict: planner gains over per-asset async scheduling are real but BOUNDED for S2 COGs. On an in-region 10 Gbps box with >= ~64 requests in flight, one-request-per-tile is already at the bandwidth bound; the planner only wins where (a) concurrency is capped (GDAL threads, zarr-python default 10, Python overhead), (b) RTT is high (remote clients), (c) IFD round trips are not cached, (d) duplicate/overlapping tiles exist, (e) tail latency/stragglers dominate, (f) memory/ordering matter for streaming into Zarr. Cannot help when bytes/BW- or decode-bound. Direct COG/raster evidence for global-vs-per-asset scheduling: NONE head-to-head; only partial direct evidence (header cache, MGRS dedupe, request-count reductions, coalescing counter-evidence). The rest is analogy (Arrow, DuckDB, Lance, zarr-python, TensorStore).
6. Biggest bytes lever is not scheduling: read amplification (a 100x100 px chip pulls a 1.35 MB 1024^2 tile = ~67x over-read) and overview selection (B04 pyramid: 160 / 41.5 / 10.8 / 2.8 / 0.7 MB by level). [BENCH-local, one scene]

### A.7 Top 3 threats to Tile-Ripper's novelty (ranked)

## PART B — Is a global read planner better than per-asset/per-chunk scheduling?

### B.1 Direct vs analogy
- DIRECT COG/raster evidence (partial): header-cache + concurrency (Rasteret, async-tiff "25x faster concurrent metadata parsing vs rasterio" [CLAIM], https://developmentseed.org/async-geotiff/latest/blog/2026/02/03/introducing-async-geotiff/ ); overlapping-tile dedupe (sentle); request-count collapse from a header index (JP2 TLM 110->3); coalescing counter-evidence (cptkirk 66 s vs 48 s, planar layout); lazycogs vs odc-stac (laptop; init 45.5 -> 0.77 s, 3-timestep spatial subset 28.8 -> 13.6 s; chunking differs) https://developmentseed.org/lazycogs/performance/ [CLAIM].
- NO head-to-head "global planner vs per-asset async" benchmark exists for rasters that I could find. Rasteret's benchmark baselines are sequential/thread-pooled rasterio, so they do not isolate planning.
- ANALOGY (strong code evidence, weaker quantitative transfer): Arrow ReadRangeCache/pre_buffer, DuckDB v2 async I/O, Lance ScanScheduler, Vortex IoService, TensorStore Batch, zarr-python sharded coalescing, fsspec.parquet, AWS CRT/Mountpoint, AnyBlob (Durner et al.).

### B.4 First-principles model
T ~= T_startup + T_plan + max( T_bw, T_lat, T_dec ) + T_tail + T_write_tail
- T_bw = B / min(NIC, C * b_conn)  (B = bytes fetched incl. over-read, NOT bytes used)
- T_lat = (R_hdr * t_hdr + R_tile * t_req) / C ; t_req(s) = b0 + s / b_conn
- T_dec = D_raw / (P * r_dec)
- T_hdr (IFD) is a dependency (file i's tile GETs wait for its header) -> minimum 2 sequential RTTs per file if headers are not cached; pipelined across files.
- Concurrency needed to saturate a link with requests of size s (derived from Little's law; same form as Arrow's MakeFromNetworkMetrics): C* = (NIC / b_conn) * (1 + b0 * b_conn / s).

Worked numbers (model.py; in-region b0=30 ms, b_conn=50 MiB/s, tile 1.29 MiB, decode 5.85 ms/tile, 8 cores):
- t_req(1.29 MiB) = 56 ms (23 MiB/s effective per connection); t_req(7.7 MiB) = 184 ms; header GET (16 KiB) = 30 ms.
- C* to saturate: 10 Gbps -> 52 (1.29 MiB), 28 (8 MiB); 25 Gbps -> 129 / 71; 100 Gbps -> 516 / 283. Remote client b0 = 150 ms: 162 / 46 (10 Gbps). => Coalescing to >= 8 MiB cuts needed concurrency ~2x in-region, ~3.5x for remote clients; if C >= C*(1.29 MiB) it buys nothing in wall-clock.
- Scenario S (small AOI x many scenes): 1 km AOI inside one tile, 400 scenes x 4 bands = 1600 tiles; B = 2.0 GiB for ~32 MB of useful pixels (~67x over-read); 10 Gbps. C=4: T_lat 22 s; C=16: 5.6 s; C=64: 1.40 s; T_bw 1.73 s; decode 1.17 s => BW-bound from C~64 on. Header GETs add 0.76 s at C=64 (-> T_lat 2.16 s, i.e. header cache = ~20%) and 3.0 s at C=16 (-> 8.6 s, 1.5x). Nothing to coalesce (1 tile/asset). Planner value here = concurrency + header index + (if available) dedupe.
- Scenario L (large AOI x few scenes): 50 km AOI = 6x6 tiles/asset, 10 scenes x 4 bands = 1440 tiles, B = 1.81 GiB. Row-contiguous runs coalesce to 6 requests/asset (240 total, ~7.7 MiB each). 10 Gbps: T_bw 1.56 s, decode 1.05 s; T_lat per-tile: 5.0 s (C=16), 1.26 s (C=64), 0.31 s (C=256); row-coalesced: 2.8 / 0.69 / 0.17 s. => BW-bound for C >= 64: coalescing = 0% wall-clock; at C=16 coalescing = 1.8x. At 25 Gbps decode (1.05 s) > BW (0.62 s): decode-bound unless codec is faster. At 100 Gbps C=256: BW 0.16 s, decode 0.53 s (16 cores) -> decode-bound.
- Laptop 1 Gbps: T_bw 15.6 s dominates; request planning irrelevant; bytes reduction (overviews 4-57x, band subsetting, partial-tile) is the only lever.
- COG geometry note: tiles are row-major, so AOI coalescing yields ~one request per tile ROW (rows are separated by the unread tiles of the scene width); across rows only when the AOI covers (nearly) the full scene width or gap < b0*b_conn (~1.5 MiB in-region). [INFER from parsed offsets]

### B.5 Regimes
- Latency/request-bound (planner can help): R*t_req/C > B/BW. Occurs when C is capped (GDAL threads, zarr-python 10, Python event-loop/GIL overhead, HTTP/1.1 pool sizes), when RTT is large (remote/cross-region clients: Pangeo's rabernat saw 66-68 s for 26 scenes x 4 bands on a us-east-1 VM vs "~10 s serially" expected by scottyhq; order-of-magnitude gain from GDAL config + co-location https://discourse.pangeo.io/t/comparing-odc-stac-load-and-stackstac-for-raster-composite-workflow/4097 [CLAIM]), when requests are tiny (<= ~1 MiB), and when headers are not cached.
- Small AOI x many scenes: request/IFD-count-bound at low C; BW-bound (dominated by tile over-read) at C >= ~64 in-region. Over-read is the real cost: choose overview level, skip fully-masked/cloudy scenes early, partial-tile prefix decode ([INFER idea; not found in any tool]).
- Large AOI x few scenes: BW/decode-bound; coalescing optional; pipeline overlap (decode+write while fetching) and fast codecs matter; planner can't beat B/BW.
- Where it provably cannot help: (1) B/BW-bound (NIC or client link), (2) decode-bound (>= ~25 Gbps with stock DEFLATE on 8 cores; JP2 sources are far worse), (3) per-tile requests already at C >= C*, (4) origin throttles (S3 5,500 GET/s/prefix; Planetary Computer 429s in sentle), (5) cached/hot data, (6) tiny jobs where startup (TLS ~0.8 s remote, STAC page 0.5-1 s, interpreter start) dominates.
- Where a planner uniquely adds: (a) dedupe of overlapping MGRS/orbit footprints (sentle: 4.3x fewer requests in the 4-tile case); (b) global concurrency budget + adaptive limit (AIMD/Vegas/gradient: https://github.com/Netflix/concurrency-limits ; BBR operating point inflight = BtlBw x RTprop https://queue.acm.org/detail.cfm?id=3022184) — none of the raster tools adapt (static 16/50/150/256); (c) hedging stragglers (Tail at Scale; AnyBlob: <5% requests >200 ms first byte; with ~1,000+ requests per job, stragglers are certain; no raster tool hedges); (d) ordering/priorities + byte backpressure so Zarr chunks complete early and memory is bounded (Lance, DuckDB governor); (e) cross-host budget when mixing providers (AWS, Azure, USGS) — matters mostly for connection/memory budget, not bandwidth; (f) whole-object GET for tiny assets (e.g. SCL 2 MB: 1 GET vs header+tile) [INFER].
- Header cost reality check: Rasteret claims GDAL does 3-6 requests/file [CLAIM]; for S2 C1 COGs the whole header is <4.3 KB so a tuned GDAL (16 KiB first read, READDIR disabled) needs 1 GET; extra requests come from LIST/sidecar probes (GDAL docs: list_dir default YES, empty_dir=NO https://gdal.org/en/stable/user/virtual_file_systems.html ) [INFER].

### B.6 Adaptive concurrency / hedging notes
- Netflix concurrency-limits: Vegas queue estimate L*(1-minRTT/sampleRTT) with alpha 2-3 / beta 4-6, Gradient2 uses long/short EWMA divergence; Little's law Limit = RPS x latency. https://github.com/Netflix/concurrency-limits [SRC doc]
- BBR (Cardwell et al. 2016): operate at inflight = BtlBw x RTprop; loss-based runs at BDP + buffer. Same shape as C* above. [SRC]
- AWS CRT is static (target_gbps/0.4) plus adaptive timeout/retry for slow uploads (tracks P90, adjusts 0.99/0.01); Mountpoint reduces parallelism/prefetch under memory pressure. [SRC]
- Hedging evidence for object stores: AWS "retry slowest 5% for large requests / after 2 s for small ones"; Durner Section 2.7. [SRC]
- S3 per-request bandwidth is capped (~95 MiB/s) and slow per connection, so a 10 Gbps link needs ~25-50 connections and 100 Gbps ~250-500 (AnyBlob/CRT agree).

## Contradictions / tensions found
1. Rasteret's headline 8-21x is vs SEQUENTIAL rasterio paths; its own blog says tile bytes are identical; vs thread-pooled rasterio it is ~8x (24 s vs 3 s) with unstated hardware. Gains attributable to header cache + concurrency, not "planning" as such. Its claim of 3-6 GDAL requests/file conflicts with my measurement that S2 headers fit in <4.3 KB (1 read for a tuned GDAL).
2. Coalescing: Rasteret/object_store/Lance/zarr/Arrow all coalesce; cptkirk found it slower (planar 64-band layout; 66 s vs 48 s) and zarr-python's PR author attributes most gain to concurrency. On S2 contiguous tiles coalescing is safe but only helps when concurrency/RTT-limited.
3. Rasteret docstring says "HTTP/2 multiplexing"; S3 and Azure blob endpoints negotiated HTTP/1.1 in my probe (h2 only on source.coop/USGS) — on AWS, concurrency = connections.
4. Coalescing thresholds differ by 250x across systems (4 KiB to 1 MiB; Arrow derives hole = TTFB x BW ~ 1.5 MiB in-region for 30 ms / 50 MiB/s). For S2 any threshold >= 8 B merges adjacent tiles; gap 0 does not.
5. Development Seed "25x metadata parsing" (async-tiff vs rasterio) vs lazycogs ~2x end-to-end vs odc-stac: different workloads, unspecified setups.
6. Earthmover (20 s per 1200^2 x 20-30 scenes on 2 vCPU), Pangeo (66 s for 26x4 scenes), scottyhq ("~10 s serial") disagree by ~10x on what "normal" is; location/config differences dominate software differences.
7. EOPF narrative ("Zarr is the format") vs reality that Earth Search S2 is COG on AWS and CDSE S2 is JP2 until EOPF goes operational (late 2026/early 2027).
