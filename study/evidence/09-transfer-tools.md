### A1. s5cmd (peak/s5cmd)
- License: MIT [SRC LICENSE https://github.com/peak/s5cmd/blob/54d6a8a955688f07e5acc40d61f9c42ceac6c33b/LICENSE]. Language: Go. ~4.2k stars; ~48 contributors (GitHub contributors API pagination).
- MAINTENANCE = STALE. Latest release v2.3.0 2024-12-16; last commit on master 2025-06-13 ("add aws-cli compatibility disclaimer"); open issue "Is this package being maintained?" (#855, opened 2026-02-02, 12 comments, last 2026-08-01) https://github.com/peak/s5cmd/issues/855 ; open "Upgrade to AWS SDK 2" #832 https://github.com/peak/s5cmd/issues/832 ; open PR "Major dependency update and bugfix" #878; a block of fix PRs filed 2026-09-17/18 (#882-#886) but none merged [SRC gh api]. Uses aws-sdk-go v1.44.298 (go.mod L6 https://github.com/peak/s5cmd/blob/54d6a8a955688f07e5acc40d61f9c42ceac6c33b/go.mod#L6); AWS SDK for Go v1 reached end-of-support 2025-07-31 https://aws.amazon.com/blogs/developer/announcing-end-of-support-for-aws-sdk-for-go-v1-on-july-31-2025/ [SRC web]. => no upstream fixes/CVE patches for the SDK it ships.
- Parallelism model [SRC]: TWO LEVELS. (1) global worker pool = semaphore of goroutines, one task per object/command, `--numworkers` default 256 (command/app.go L18,L34-37 https://github.com/peak/s5cmd/blob/54d6a8a955688f07e5acc40d61f9c42ceac6c33b/command/app.go#L18 ; parallel/parallel.go L9-L34 minimum 2; negative value = N x NumCPU). (2) per-object part parallelism via s3manager.Downloader: `cp --concurrency` default 5, `--part-size` default 50 MiB (command/cp.go L29-30 https://github.com/peak/s5cmd/blob/54d6a8a955688f07e5acc40d61f9c42ceac6c33b/command/cp.go#L29-L30; storage/s3.go L603-626 "Makes a single GetObject call if concurrency is 1"). Product of the two is NOT capped: up to 256 x 5 = 1,280 in-flight GETs; code has an fd-limit warning telling users to lower -numworkers (cp.go ~L415) [SRC]. README itself says for few large files numworkers does not help, raise --concurrency.
- Ranged GETs within one object: yes, but only part-wise to fill a whole file (SDK v1 s3manager). No user-specified Range anywhere (rg "range" in storage/ and command/ finds only loop vars) [SRC] => CANNOT read arbitrary spans. `cat` has no offset/count.
- Connection reuse: HTTP client = aws-sdk-go default `http.DefaultClient` (vendor/.../aws/defaults/defaults.go#L59; s5cmd only overrides it for --no-verify-ssl, storage/s3.go L1276, L1411) [SRC]. Go DefaultTransport keeps MaxIdleConnsPerHost = 2 (https://pkg.go.dev/net/http#Transport) => with 256 workers most connections are closed after use and re-dialed (extra TCP+TLS handshake per request) [INFER - not measured; verify with ss/pcap]. Irrelevant for 200 MB objects, relevant for ~1 MB requests.
- Retry: `--retry-count` default 10 (app.go L19); customRetryer adds InternalError/SlowDown/connection reset to SDK DefaultRetryer (storage/s3.go L1380-1405) [SRC]. No client-side token bucket / rate limit.
- Anonymous: `--no-sign-request` => AnonymousCredentials (storage/s3.go L1242-1244) [SRC]. S3 API only (no Azure SAS, no plain HTTP).
- Listing / overhead [SRC command/expand.go L16-L40]: wildcard => ListObjectsV2; explicit remote key => no list, but cp does Stat (HEAD) on source and destination (cp.go L525, L755, L951, L1066) => >= 2 requests per object. `s5cmd run file` batches many `cp` lines through the same pool.
- Throughput claims: README quotes a third-party Medium post (Joshua Robinson): download "can saturate a 40Gbps link (~4.3 GB/s)", aws-cli 375 MB/s, s3cmd 85 MB/s; uploads 32x s3cmd/12x aws-cli https://github.com/peak/s5cmd#readme . I could not open the Medium post (HTTP 403) so hardware/store details are UNVERIFIED by me; a web-search summary says it used a Pure FlashBlade object store, i.e. not AWS S3 [CLAIM]. A Hacker News commenter says the s5cmd benchmark numbers came from a custom S3-emulating server on the client machine and could not be reached on real S3 https://news.ycombinator.com/item?id=44249137 [CLAIM, anecdote]. s5cmd's own benchmark/bench.py is a regression harness (hyperfine, two s5cmd builds), not a cross-tool benchmark https://github.com/peak/s5cmd/blob/54d6a8a955688f07e5acc40d61f9c42ceac6c33b/benchmark/README.md [SRC].
- Independent data: (a) HN anecdote, r6a.16xlarge (25 Gbps), 10 GB single object, same-region S3 via VPC endpoint, to /dev/shm: s5cmd default settings 24 s (~0.42 GB/s; = 5 connections x ~83 MB/s [INFER]); Python tool s3pd 10 s same workers, 6 s with 80 workers (~1.6 GB/s); commenter concludes S3 caps ~1.6 GB/s per instance/object https://news.ycombinator.com/item?id=44249137 [CLAIM, single anecdote, flags unspecified]. (b) DoiT [BENCH-partial]: c7gn.16xlarge (200 Gbps, 64 cores), 12x gp3 RAID0, 4 TB per tier (5 GB x819, 1 GB x4,096, 32 MB x131,072, 256 KB x16,777,216), s5cmd v2.2.2 DEFAULT flags vs aws-cli (classic, default and tuned 64/1GB/256MB); reported only fold-changes: download 15-17x faster than aws-cli default (30.5x for 256 KB files), 6.4-8.7x vs tuned, "minimal gain" for very large files tuned https://www.doit.com/blog/save-time-and-money-on-s3-data-transfers-surpass-aws-cli-performance-by-up-to-80x ; script/terraform public https://github.com/doit-mattporter/aws_cli_vs_s5cmd (script: benchmarking/startup_benchmarking_script.sh; README says full run takes ~5 weeks). Region not stated; absolute MB/s not published; pre-dates CRT-by-default (see A3) => multiples are stale for aws-cli on EC2 today [INFER].
- Other evidence rated weak: blacha/s3-client-benchmark uses a local mock S3 server on a 10 GbE LAN (pushed 2021) https://github.com/blacha/s3-client-benchmark [SRC]; scttfrdmn/cargoship#35 measured 10,000 tiny files (~20 MB): s5cmd 8.17 s vs aws-cli 63.5 s (hardware unstated, ~1.2k files/s) https://github.com/scttfrdmn/cargoship/issues/35 [CLAIM].

### A2. rclone
- License: MIT (COPYING https://github.com/rclone/rclone/blob/4f19e9cd6f442282d7fa8d5fdbd28ebb68be1131/COPYING). Go. ~60k stars, ~1.2k contributors, release cadence ~monthly (v1.75.2 on 2026-10-09; v1.75.1 2026-09-04; v1.75.0 2026-07-31) [SRC gh]. Uses aws-sdk-go-v2 (go.mod).
- Parallelism [SRC fs/config.go]: `--transfers` default 4 (L65-66); `--checkers` default 8 (L60-61); `--multi-thread-streams` 4, `--multi-thread-cutoff` 256 MiB, `--multi-thread-chunk-size` 64 MiB, `--multi-thread-write-buffer-size` 128 KiB (L448-466) https://github.com/rclone/rclone/blob/4f19e9cd6f442282d7fa8d5fdbd28ebb68be1131/fs/config.go#L448-L466 ; `--buffer-size` 16 MiB (L341); `--tpslimit` default 0 = off + `--tpslimit-burst` 1 (L286-295); `--max-connections` default 0 = unlimited (L554); `--retries` 3, `--low-level-retries` 10, `--contimeout` 1m, `--timeout` 5m. S3 backend: `--s3-chunk-size` 5 MiB, `--s3-upload-concurrency` 4, upload_cutoff 200 MiB (uploads only) (backend/s3/s3.go L356-365, L975-981).
- Multi-thread download gate (fs/operations/multithread.go L25-55 https://github.com/rclone/rclone/blob/4f19e9cd6f442282d7fa8d5fdbd28ebb68be1131/fs/operations/multithread.go#L25-L55): only if streams > 1 AND size >= cutoff AND dest supports OpenWriterAt/OpenChunkWriter (local disk does). IMPLICATION [INFER]: S2 B02/B03/B04/B08 (~190 MiB) are BELOW the default 256 MiB cutoff => each is ONE connection; with default --transfers 4 you get ~4 connections total. Whole-object S7 on S2 must raise --transfers (and lower the cutoff only if per-object parallelism is wanted).
- Rate limiting designs [SRC]: (1) --tpslimit = golang.org/x/time/rate token bucket, one Wait per HTTP transaction, global (fs/accounting/tpslimit.go https://github.com/rclone/rclone/blob/4f19e9cd6f442282d7fa8d5fdbd28ebb68be1131/fs/accounting/tpslimit.go). (2) per-backend "pacer": S3 uses pacer.NewS3(minSleep 10ms, maxSleep 2s, attack 1, decay 2) - sleep time is shared state: on consecutive retries it grows geometrically; on success it decays to 0 (below minSleep => 0); honors Retry-After (lib/pacer/pacers.go L220-290 https://github.com/rclone/rclone/blob/4f19e9cd6f442282d7fa8d5fdbd28ebb68be1131/lib/pacer/pacers.go#L220-L290 ; backend/s3/s3.go L1847). So in steady state the S3 pacer adds NO throttling. (3) HTTP transport: MaxIdleConnsPerHost = 2*(checkers+transfers+1) = 26 by default, IdleConnTimeout 60 s, TLS handshake timeout = contimeout (fs/fshttp/http.go L235-239, L280 https://github.com/rclone/rclone/blob/4f19e9cd6f442282d7fa8d5fdbd28ebb68be1131/fs/fshttp/http.go#L235-L239). HTTP/2 can be disabled (`--disable-http2`).
- Partial-range reads: `rclone cat --offset N --count N` reads ONE span of ONE object per process (cmd/cat/cat.go L30-33) [SRC]; `rclone copy` cannot. Mount/serve could do ranges but are FUSE/HTTP front-ends, not span-list batchers.
- Hosts: S3 (anonymous when no keys and env_auth=false, backend/s3/s3.go L1507-1511), Azure Blob (sas_url option, anonymous, azureblob.go L736, L1974), generic HTTP backend (backend/http) => the only tool here covering all three S2 host types.
- Listing/overhead: copy of a prefix = ListObjectsV2 (list_chunk 1000) + per-file dest check (size+modtime) + HEAD on source for objects in some paths; avoidable flags: `--files-from list --no-traverse --no-check-dest`, `--s3-no-head-object` ("do not do HEAD before GET", s3.go L510-511), `--ignore-checksum`, `--ignore-times`/`--size-only`. [flags exist in source; I did not run them - combination untested]
- AWS's own benchmark harness drives rclone as: `rclone copy ... --transfers N --s3-upload-concurrency N --multi-thread-streams N --ignore-times --s3-disable-checksum` with N = target_Gbps/0.4 (runner/rclone.py L98-144 https://github.com/awslabs/aws-crt-s3-benchmarks/blob/125c92e12e9c6eee2325525d3ffd1db58babfbec/runners/s3-benchrunner-3p/runner/rclone.py#L98-L144) [SRC].
- Independent numbers: rclone forum threads (EC2 c6in.32xlarge scripting of flags; 10 GbE box capped ~900 Mbps at --transfers 16; "2x slower than aws s3 cp" at defaults) are anecdotes without method https://forum.rclone.org/t/maximum-resources-usage/36007 , https://forum.rclone.org/t/rclone-sync-s3-gbps/30846 , https://forum.rclone.org/t/rclone-s3-backend-copy-is-2x-slower-than-aws-s3-cp/27321 [CLAIM]. zeroservices.eu: rclone --transfers 32 uploaded 86,618 files (1.6 GB) to a non-AWS S3 in 39.4 s (~2.2k files/s) vs aws-cli 349.7 s https://lp.zeroservices.eu/articles/s3-client-performance-rclone-minio-aws/ [CLAIM, uploads, non-EC2]. No rigorous rclone download benchmark on EC2/S3 found.

### A3. aws-cli v2 (classic vs CRT)
- License Apache-2.0 (LICENSE.txt; GitHub reports NOASSERTION because of the preamble) https://github.com/aws/aws-cli/blob/9469a4d8191c8139b54dd119526648d29a4b5f72/LICENSE.txt . Python (+ CRT in C via awscrt). Releases essentially daily (2.37.12 on 2026-10-09). Backing lib: awslabs/aws-c-s3 Apache-2.0, C, v1.3.1 (2026-10-05).
- CLASSIC client defaults [SRC awscli/customizations/s3/transferconfig.py L26-L37 https://github.com/aws/aws-cli/blob/9469a4d8191c8139b54dd119526648d29a4b5f72/awscli/customizations/s3/transferconfig.py#L26-L37]: max_concurrent_requests 10, max_queue_size 1000, multipart_threshold 8 MB, multipart_chunksize 8 MB, io_chunksize 256 KB. Thread pool (s3transfer); the client is built without a Config so botocore's max_pool_connections stays at 10 (awscli/botocore/endpoint.py#L39) - raising max_concurrent_requests above 10 therefore likely creates then discards extra connections [INFER from SRC; unverified empirically]. Python GIL limits parallel CPU work (DoiT's explanation, [CLAIM]).
- CRT client: preferred_transfer_client = auto | classic | crt. **NEW (CHANGELOG): CRT is now enabled by default on EC2**: 2.37.2 c7*/m7*/r7* etc.; 2.37.6 c6*/m6*/r6*; 2.37.8 c5/m5/r5; 2.37.11 "t4g, t3a, t3, t2, and any other instance families ... including all future families" https://github.com/aws/aws-cli/blob/9469a4d8191c8139b54dd119526648d29a4b5f72/CHANGELOG.rst#L42 [SRC]. Auto resolution (factory.py L186-L255): not S3->S3; host is EC2 (Linux); no unsupported settings (max_bandwidth, retry_mode adaptive, max_attempts outside 2..64, non-seekable stream upload); AND no other aws-cli process holding the CRT process lock (`_is_crt_client_running_in_other_aws_cli_process`) - otherwise silently classic. Doc: https://github.com/aws/aws-cli/blob/9469a4d8191c8139b54dd119526648d29a4b5f72/awscli/topics/s3-config.rst#L326-L430 . => on a laptop `aws s3 cp` = classic; on EC2 it is CRT. Always pin it.
- CRT knob mapping [SRC factory.py L85-L89, L394-L396, L420-L440]: max_concurrent_requests -> CRT `max_active_connections_override` (ONLY if set explicitly); multipart_chunksize -> part_size (if unset: None => CRT dynamic part size); multipart_threshold -> multipart_upload_threshold; target_bandwidth -> target_throughput. Default target: explicit `crt` => max(detected recommended, 10 Gbps); auto => detected NIC, 4 Gbps if undetectable (docs s3-config.rst L366-L420). max_queue_size and io_chunksize ignored under CRT.
- CRT internals [SRC aws-c-s3 e05c129]: ideal connections = max(10, ceil(target_Gbps / 0.4)) (s3_client.c L63-L77, L180-L184; TODO in source: "expect lower throughput for small objects") https://github.com/awslabs/aws-c-s3/blob/e05c12923b84a801878e2f6fc56f10403f02f7be/source/s3_client.c#L59-L77 ; default target 10 Gbps => 25 connections; in-flight requests = 4 x connections (L60); `max_active_connections_override` can only LOWER the ideal count (L292-L296) => to raise concurrency you must raise target_bandwidth, not max_concurrent_requests. Part size: if not user-set, "optimal range size" = clamp(memory_limit / connections / 3, 8 MiB, 5 GiB) and per request min(that, estimated original upload part size parsed from the ETag "-N") bounded to 8 MiB..2 GiB (s3_util.c L883-L930, L934-L980; s3_auto_ranged_get.c L1075-L1125). First GET is a ranged GET of part_size (no HEAD) UNLESS whole-object checksum validation is on, in which case a HEAD is issued first (s3_auto_ranged_get.c L158-L223). aws-cli default response_checksum_validation = when_supported (botocore/configprovider.py L180-L185) => CRT downloads in aws-cli do HEAD + ranged GETs per object; set `response_checksum_validation = when_required` for parity with an engine that does no checksum validation [INFER, unverified in a trace]. CRT accepts a user Range header per meta-request (GET_OBJECT_WITH_RANGE) but the aws-cli exposes none, and there is no multi-range API.
- Parallelism per object vs per part: CRT is per-meta-request (one object) split into parts; connections are a global pool across meta-requests; the CLI submits many objects to one CRT client (so object-level and part-level parallelism share ONE global budget - unlike s5cmd's product).
- Anonymous: `--no-sign-request` supported on the CRT path (factory.py: credentials provider only if sign_request) [SRC]. S3 only (no Azure/HTTP). No manifest input to `aws s3 cp` (no --files-from): per-key invocations cost process start-up each and, under `auto`, concurrent invocations lose the CRT lock; use `--recursive --exclude/--include` (does a list) or a CRT harness runner (below).
- Reproducible harness (important): awslabs/aws-crt-s3-benchmarks (Apache-2.0) with runners crt-c, crt-python, boto3-crt/classic, cli-crt/classic, java, cpp, sdk-rust-tm and a third-party runner for s5cmd and rclone; workloads are JSON task lists (download-5GiB-1x/10x/20x, 30GiB, 64KiB x1,000, 256KiB x10,000, Caltech256, c4-en, download-max-throughput "don't touch disk"); runner CLI takes TARGET_THROUGHPUT Gbps; requires credentials with read+write to a bucket; no results are published in the repo https://github.com/awslabs/aws-crt-s3-benchmarks/blob/125c92e12e9c6eee2325525d3ffd1db58babfbec/README.md [SRC]. Its 3p runner sets s5cmd `cp --concurrency N --retry-count 3` (NOT --numworkers) and rclone `--transfers N --s3-upload-concurrency N --multi-thread-streams N`, N = int(target_Gbps/0.4) (runners/s3-benchrunner-3p/runner/s5cmd.py L58-L85).
- Published numbers: AWS Storage Blog - trn1n.32xlarge, CLI with CRT off/on on Caltech-256 (30,607 files, avg 40 kB, 1.1 GB), Caltech-256-WebDataset (100 MB shards), C4-en (1,024 x 320 MB), 7.6 GB checkpoint: "2 - 6x" speedup; chart only, region/settings not stated https://aws.amazon.com/blogs/storage/improving-amazon-s3-throughput-for-the-aws-cli-and-boto3-with-the-aws-common-runtime/ [CLAIM with public datasets/harness]. No GB/s tables.

### A4. AzCopy v10
- License MIT; Go; ~700 stars, ~66 contributors; v10.32.8 2026-08-27, v10.33.0-beta 2026-07-31; commits to 2026-10-09 [SRC gh]. https://github.com/Azure/azure-storage-azcopy
- "Auto-tunes concurrency" - VERIFIED BUT CONDITIONAL. Default main pool = 32 if CPUs <= 4, else min(300, 16 x NumCPU), FIXED (ste/concurrency.go L176-L215 https://github.com/Azure/azure-storage-azcopy/blob/35dc27add1e640506b1221172f6c0f3d317dff65/ste/concurrency.go#L176-L215). Auto-tuning runs only when AZCOPY_CONCURRENCY_VALUE=AUTO or in `azcopy benchmark` mode; then it starts at 4 and may grow to 3000 (L194, L213); MS docs confirm "AUTO ... always run the same automatic tuning process that it uses in benchmark tests" https://learn.microsoft.com/en-us/azure/storage/common/storage-use-azcopy-optimize [SRC].
- Tuner algorithm (ste/concurrencyTuner.go L139-L250 https://github.com/Azure/azure-storage-azcopy/blob/35dc27add1e640506b1221172f6c0f3d317dff65/ste/concurrencyTuner.go#L139-L250): measures Mbps; multiplier 4 up to 256 connections, then 2; accepts a step only if throughput gained >= 20% of the linear expectation (fudgeFactor 0.2); else backs off to the previous level and divides (multiplier-1) by 5; stops when multiplier < 1.19; CPU-aware (high CPU flagged "may be limited by CPU"); benchmark mode is more aggressive (does not back off on retries below 256, probes higher when >11 Gbps seen). It is a ONE-SHOT hill-climb: after it settles it holds the value ("tuning already finished") - no continuous adaptation [SRC].
- Chunking: downloads are ranged GetBlob calls of `BlockSize` (ste/downloader-blob.go L179 Range{Offset,Count}); `--block-size-mb` default 0 = auto: 8 MiB base, doubled to stay <= 50,000 blocks (mgr-JobPartTransferMgr.go L371-L392; common/fe-ste-models.go L1157) [SRC; confirmed for the upload path, download path reads info.BlockSize - treat 8 MiB as likely, unverified]. HTTP transport: IdleConnTimeout 180 s, TLS handshake timeout 10 s, MaxConnsPerHost = dials-per-CPU x NumCPU (ste/mgr-JobPartMgr.go L98-L106); retries: 5 per download body, delay 1 s -> 60 s, try timeout 15 min (ste/xfer.go L36-L48).
- Docs guidance [SRC learn.microsoft.com]: run one AzCopy instance per client; jobs < 10M files; `--log-level=ERROR`; `--check-length=false` for many small files; AZCOPY_BUFFER_GB; `azcopy benchmark` prints recommended concurrency. Job state is written to local plan/log files (AZCOPY_LOG_LOCATION, AZCOPY_JOB_PLAN_LOCATION) [SRC common/environment.go] - disk side effects in a benchmark.
- Auth: SAS in URL or Anonymous (public containers) (azcopy/credentialUtil.go L117, L199, L317, L373) [SRC] => works with Planetary Computer SAS URLs.
- Range reads of arbitrary spans: none (no range flag in cmd/copy.go; rg empty). Azure limits [SRC docs]: single block blob target 3,000 req/s; GPv2 default egress 200 Gbps (Americas/Europe/APAC list) else 50 Gbps; 503/500 on hot partitions - https://learn.microsoft.com/en-us/azure/storage/blobs/scalability-targets , https://learn.microsoft.com/en-us/azure/storage/common/scalability-targets-standard-account . No published AzCopy throughput benchmark with method found.

### A5. gcloud storage / gsutil
- gcloud storage is part of the Google Cloud CLI (closed repo; Apache-2.0 for the SDK distribution per Google; not verified here). Python. gsutil is being REMOVED from the default Cloud CLI packages from March 2027 (secondhand from GitHub issues relaying a 2026-07-20 Google email, e.g. https://github.com/kubernetes/kubernetes/issues/142384 ; transition guide https://docs.cloud.google.com/storage/docs/gsutil-transition-to-gcloud) [CLAIM relayed].

Sliced downloads need compiled crcmod/google-crc32c; docs: https://docs.cloud.google.com/storage/docs/sliced-object-downloads .

### A6. aria2
- License GPL-2.0 (COPYING + OpenSSL linking exception) - fine to run as a comparator, not to link. C++. Latest release 1.37.0 on 2023-11-15; master commits through 2026-06-25 are dependabot-style; 1,182 open issues [SRC gh].

### B1. Right "whole-object download" comparator (S7) and settings
Recommendation: S7 is a SET, not one tool, because the three S2 hosts need different APIs:
- S7-S3 (headline for sentinel-cogs, us-west-2, EC2 in-region): **aws-cli v2 with explicit CRT** (vendor-maintained, daily releases, default on EC2 now, in AWS's own reproducible harness). Settings: `aws configure set default.s3.preferred_transfer_client crt`; `default.s3.target_bandwidth <NIC>Gb/s` (units are bits; powers of 2 per doc; default under explicit crt = max(detected, 10 Gbps) => 25 conns, 4x in-flight=100); leave multipart_chunksize unset (dynamic >= 8 MiB) or sweep 8/16 MiB; `default.s3.response_checksum_validation when_required` OR record that default does HEAD per object; `--no-sign-request`; target tmpfs (/dev/shm) for the network ceiling and local NVMe/EBS for the realistic case. Do NOT rely on max_concurrent_requests (it can only lower CRT concurrency). Because aws s3 cp has no manifest, run one `--recursive --exclude '*' --include 'key'...` invocation or use the harness `crt-c`/`crt-python` runner with a workload.json task list (need a bucket copy if the runner can't do unsigned requests - open question).
- S7-S3-secondary: **s5cmd v2.3.0** (still the de-facto Go worker-pool reference, and AWS's harness benchmarks it) but report it as "tuned default": `s5cmd --no-sign-request --numworkers W --retry-count 10 run cmds.txt` with `cp --concurrency 5 --part-size 50` defaults (200 MB object = 4 parts) => in-flight ~ W x 4; sweep W in {16,32,64,128,256}; AWS's own formula: N = ceil(T_Gbps/0.4) total connections (10 Gbps -> 25, 25 Gbps -> 63, 100 Gbps -> 250). Flag staleness (SDK v1 EOL) in the write-up.
- S7-cross-host: **rclone** (S3 anon + Azure sas_url + HTTP). Because S2 bands (~190 MiB) are below the 256 MiB multi-thread cutoff, the settings that matter are `--transfers N` (default 4!), `--checkers N` (default 8), `--files-from list --no-traverse --no-check-dest --ignore-times --ignore-checksum`, `--s3-no-head-object`; optionally `--multi-thread-cutoff 32M --multi-thread-streams 4 --multi-thread-chunk-size 16M` to split bands. Match AWS harness: transfers = streams = T/0.4 as an upper "tuned" arm; defaults as the "untuned" arm. [flag combination not run]
- S7-Azure (Planetary Computer): **AzCopy v10.32.8** with SAS URLs; default concurrency 16 x CPUs (<=300; 32 if <=4 CPUs); compare `AZCOPY_CONCURRENCY_VALUE=AUTO` (hill-climb, start 4, max 3000) and fixed; `--check-length=false --log-level=ERROR`; run `azcopy benchmark` first. Run from an Azure VM in the same region as the storage account (PC S2 account sentinel2l2a01 region per sibling note 05) or the numbers are WAN-bound.
- Plain-HTTPS-URL arm (the engine's actual input = STAC hrefs): `aria2c -i urls.txt -j W -x 16 -s 16 -k 4M --file-allocation=none` and/or `curl --parallel --parallel-max N`; both HTTP/1.1 here.
- For each arm publish two bars: defaults and best-of-sweep (knee), with CPU %, connection count (ss -tn), and requests/object; also repeat from a laptop to avoid claiming in-region results elsewhere.

### B3. Designs worth copying for the scheduler
1. ONE global in-flight budget (CRT: connections = target/0.4, in-flight = 4x connections, queue/prepare stage overlaps signing and request prep with network) rather than s5cmd's objects x parts product (256 x 5, fd exhaustion, MaxIdleConnsPerHost churn). [SRC]
2. Part/range sizing from memory budget: CRT range = clamp(memory_limit/connections/3, 8 MiB, ...) and matching original multipart part boundaries via ETag "-N" (aws-c-s3 s3_util.c L883-L980). For COGs: choose request size from tile byte-counts instead, but the memory-derived bound and "match stored part boundaries" are cheap ideas. [SRC]
3. "No HEAD": first request is a ranged GET that discovers size (Content-Range); optional object_size_hint avoids range probing for small objects (s3_auto_ranged_get.c L196-L223). For an engine with TIFF header caches the analogue is the header GET. [SRC]
4. AzCopy's one-shot hill-climb for concurrency: start 4, x4 up to 256 then x2, require >= 20% of linear gain per step, back off + shrink multiplier, stop at <1.19, CPU-aware; benchmark mode more aggressive. Use as a cheap warm-up probe (30-60 s) per host to set connection count, then hold; add periodic re-probe (AzCopy does not). [SRC]
5. rclone: separate (a) provider-quota token bucket (--tpslimit/burst via x/time/rate) from (b) failure pacer (S3 pacer: shared sleep state, attack/decay, honors Retry-After, 10 ms min / 2 s max) and (c) --max-connections cap; HTTP idle pool sized from concurrency (2 x (checkers+transfers+1)). Maps onto CDSE (4 connections), PC SAS throttling, S3 SlowDown. [SRC]
6. gcloud: pick presets by workload shape (multi-file vs single-file, CPU count) and size slices at 5 MiB for many-file runs - evidence that 5-8 MiB is the common part size across tools. [SRC mirror]
7. warp: report TTFB percentiles and throughput per interval; AnyBlob/Lance-style hedging of slowest 5% (AWS guidance: retry slowest 5% of >128 MB requests; retry <512 KB GET after 2 s on a new connection/new DNS answer) [SRC AWS doc]. No tool here implements hedging for GETs (sibling 08 found none either).
8. Anti-patterns: s5cmd's DefaultTransport idle limit; aws-cli classic's pool of 10 vs raised thread count; static per-connection constant (CRT 0.4 Gbps) with no feedback.

### B4. Pitfalls when using them as baselines
- aws-cli: result depends on host (CRT on EC2 since 2.37.x, classic elsewhere) and on concurrent invocations (CRT lock => silent classic fallback under auto); set preferred_transfer_client explicitly and log `aws --debug` ("Auto resolved s3 transfer client to"). Under CRT max_concurrent_requests can only reduce; target_bandwidth is the throttle; default explicit-crt target >= 10 Gbps. Classic: pool size 10 [INFER]; many-small-files listing is serial ListObjectsV2. Checksum validation default => extra HEAD per object. `--recursive` needs a list; no manifest.
- s5cmd: stale (SDK v1 EOL); marketing numbers not reproduced on real S3 (HN); defaults 256 workers x 5 parts can exceed fd limits; idle-connection limit [INFER]; per-object HEAD(s); wildcards => List; S3 only; `--no-sign-request` OK.
- rclone: defaults transfers 4 / checkers 8; multi-thread cutoff 256 MiB > S2 band size; dest check (size+mtime) and optional hash verification add CPU/requests; listing ListObjectsV2; flags above remove them; log retries (low-level-retries) can hide throttling; one process-global token bucket if --tpslimit set.
- AzCopy: only tunes with AUTO/benchmark; writes plan+log files; recommends single instance per VM; one job state per run; SAS expiry; needs an in-region Azure VM for meaningful numbers; Azure partition throttling 503/500 not S3 SlowDown semantics.
- aria2: -x default 1; HTTP/1.1; GPL; JSON-RPC off.
- Every tool: whole-object download of a ~200 MB band for a 100x100 px chip moves ~150x more bytes than the engine; S7 is a ceiling for FULL-tile acquisition and a floor-cost check, not a like-for-like AOI baseline. Write to tmpfs to isolate network; also run local-disk arm because rclone multi-thread/AzCopy do parallel random writes.
- Anonymous support: s5cmd --no-sign-request; aws-cli --no-sign-request (CRT path unsigned ok); rclone no keys + env_auth=false; AzCopy anonymous public blob or SAS in URL; aria2/curl any HTTPS URL. Azure SAS URL support: AzCopy yes, rclone azureblob sas_url yes, aria2/curl yes (URL carries SAS), s5cmd/aws-cli no.
- Egress path: on EC2 use an S3 gateway endpoint; otherwise the 5 Gbps (<32 vCPU) / 50% (>32 vCPU) internet-gateway rule caps every tool identically.

## C. Contradictions
====================================================================
1. s5cmd "saturates 40 Gbps / 4.3 GB/s" (README) vs HN: the numbers came from a local S3 emulator and real S3 gives ~0.42 GB/s with defaults on one 10 GB object. I could not read the Medium post (403), so the FlashBlade vs emulator detail is unresolved.
2. "AzCopy auto-tunes concurrency" - true only with AZCOPY_CONCURRENCY_VALUE=AUTO or benchmark mode; default is fixed 16 x CPUs (cap 300).
3. aws-cli doc text says CRT "optimized for" p4d/p5/trn1 only, but the CHANGELOG (2.37.2-2.37.11) enables CRT-by-default on all EC2 families; "optimized" governs fallback/exclusion rules, not eligibility. DoiT's 15-30x multiples compare s5cmd with the classic client and are stale for current EC2 defaults.
4. "Per-connection S3 limit 5 Gbps" (search snippet of a re:Post article) vs AnyBlob per-request cap ~95 MiB/s (=0.8 Gbps): different layers (EC2 flow limit vs S3 request).
5. CRT assumes 0.4 Gbps (50 MB/s) per connection; AnyBlob measures median 55-60 MiB/s (>= 0.46 Gbps) - consistent for 16 MiB requests, wrong (too high) for ~1 MB requests (CRT's own TODO).
